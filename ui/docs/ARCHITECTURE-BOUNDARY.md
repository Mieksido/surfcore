# 四层架构与内核边界（红线）

> 2026-11-11 用户严肃纠正。此文件是 UI/接口设计的**最高约束**，优先于任何临时的后端交接、兼容接口或“先跑起来”的便利。
> 违反此文件的实现，不得以“旧运行时兼容”“临时桥”为由继续保留在内核入口。

---

## 1. 架构只有四层

```text
内核
  └─ 大适配器
       ├─ 小适配器
       │    └─ 模块
       └─ 小适配器
            └─ 模块
```

- 大适配器可以连接多个小适配器和它们对应的模块。
- **没有第五层**；旧运行时兼容前缀、QQ 桥、语音包管理器、HTTP 代理都不是“层”。
- UI 是壳，不是层；壳只能展示内核/适配器给出的中性信息。

### 1.1 本体 / mod 视角（2026-11-11 用户补充）

可以把架构理解成：

| 角色 | 组成 | 性质 |
| --- | --- | --- |
| **本体** | **内核 + 大适配器** | 必须存在、平台无关、可独立启动；不知道任何 mod 的平台实现 |
| **mod** | 小适配器 + 对应模块 | 可选、可插拔、声明能力；可安装/卸载/失败，不影响本体启动 |

规则：

1. 本体不 import mod 代码，不读 mod 的 state，不知道 mod 的端口/路径/进程/平台名。
2. 本体只通过**能力声明 + 中性 intent/transport/opaque payload** 使用 mod。
3. 大适配器是本体和 mod 的边界：注册、选择、启停、配额、错误归一都在这里；内核只做中性决策。
4. mod 缺失/损坏/未安装是正常状态：显示「未安装/待接入」，本体照常启动，不能把“先启动某个外部桥”作为本体启动前提。
5. UI 可以展示“本体状态”和“mod 可用性”，但不要把 mod 的平台名写成内核能力。
6. 语音包管理器 / QQ 桥是 **mod 侧的旧实现**，不是本体；语音能力缺失时本体仍成立。

---

## 2. 内核红线

内核**绝对不允许**：

1. 出现任何外界平台的名字：QQ、B站、桌宠、网页、微信、抖音……都不行。
2. 知道任何外界代码、路径、进程、端口、桥接、配置文件。
3. 直接/间接依赖外部进程或桥接才能启动语音；例如“先启动 QQ 桥接，语音才能用”。
4. 把某个平台的安装器、TTS 引擎、API 客户端当成内核能力。
5. 用平台名做分支、日志、错误提示、按钮文案。

内核**只认识**适配器传进来的中性信息：

```text
SourceId          不透明来源 ID（UI 才翻译成 QQ / B站 / …）
Capability        能力声明（能做什么，不包含平台实现）
Intent            中性意图（如 voice.speak / voice.stop）
TransportId       不透明 transport 标识
Opaque payload    适配器自己解释的数据
```

启停、安装、路由、平台选择由**大适配器编排**，小适配器/模块执行；内核只做决策、闸门、路由选择的中性部分。

## 3. 正确的语音链路

```text
内核 voice 决策/闸门
  → 中性 intent（合成/停止/选择 voice profile）
  → 大适配器 voice 能力（本体边界）
  → 选择 mod：小适配器/模块（本地 TTS、云端 TTS、……）
  → 外部服务/进程
```

- 内核不知道“QQ 桥接”，也不知道“voice-local / voice-cloud”的安装细节；这些是 mod 侧实现/实例名，不是本体概念。
- 大适配器负责“用哪个 mod”，必要时在适配器内部处理平台差异；mod 缺失时返回中性不可用，不阻塞本体。
- UI 只读中性状态；启动/停止通过中性适配器控制面，不直连外部桥。

## 4. 我犯的错（必须记住）

1. 把旧运行时的 `/surfcore-api/voice` 兼容前缀当成了内核语音控制面。
2. `VoicePage` 直接调用这个前缀；该前缀实际转发到 **QQ 桥接的语音包管理器**。
3. UI 文案写了“试合成 · 不发 QQ / 不会发送到 QQ”。
4. 错误提示写了“先启动 QQ 桥接”，等于把外部桥接当成语音启动前提。
5. 把“旧桥能跑”误当成“内核已具备语音能力”，还按这个前提设计了安装/启动/试合成按钮。

**责任在 UI 设计，不在后端代码。**
后端 `VOICE-API-CONTRACT.md` 已写明“旧运行时插件新增，转发旧桥语音包管理器；不是新层”；我看到了这句话，却仍然把它做成了内核入口。旧桥本身只是兼容面；错在 UI 把它抬成了内核能力。

## 5. 处理决定（已更新）

- **语音页接同源代理**：UI 只调 `16460` 的 `/surfcore-api/voice/*`；宿主代理内部转发到语音控制面（4317），token 由宿主带。
- 4317 只是宿主内部/调试控制面，**不是 UI 入口**；UI 不填地址/token，不处理 CORS。
- 语音仍是内核感官；模型/工件/运行时在 `kernel/voice`，由控制面调用内核公共面，不由 UI 直接拉进程。
- `/surfcore-api/voice` 现在是宿主同源代理，不是旧 QQ 桥兼容口；旧兼容页/旧桥 API 文件已删除。
- UI 不显示“启动控制面”按钮（控制面没有该接口）；控制面未启动时显示错误 + 重试，不伪造状态。
- 模型导入/试合成/服务商配置按 `VOICE-UI-API.md`；没有的音频/进度/上传能力不伪造。

## 6. 未来验收清单

- [ ] 内核页面/组件/文案里 `grep` 不到 QQ、B站、桌宠、网页等平台名（UI 的来源标签除外）。
- [ ] 语音页只请求同源 `/surfcore-api/voice/*`；不直连 4317、不填 token、不处理 CORS。
- [ ] 没有“先启动 QQ 桥接/外部进程才能用语音”的提示或前置条件。
- [ ] 模型装载/卸载/选择通过控制面；UI 不读 state、不直接拉起进程。
- [ ] 控制面 token 只在宿主内部；UI/日志/localStorage 都不存 token。
- [ ] 平台显示只由 UI 的 SourceId 映射负责；内核/适配器只传不透明 ID。
- [ ] 记忆等旧运行时数据接口也只作为**适配器兼容面**看待，不称为内核原生能力；迁移后由适配器中性接口替换。
