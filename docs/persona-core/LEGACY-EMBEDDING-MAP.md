# 旧 SurfCore 嵌合图（旧部件 → 新架构）

> 目的：回答"旧的那一坨，具体装进新架构的哪一格、怎么接"。
> 阶段：**形状层**（不写字段）。配套：[适配器形状](ADAPTER-SHAPE.md) · [迁移总计划](MIGRATION-PLAN.md) · [记忆内核形状](MEMORY-KERNEL-SHAPE.md)
> 立文 2026-11-09。所有旧模块行数/位置来自 `dev@856e924` 实测。

---

## 0. 一句话结论

> **`bridge.js`（17,801 行）不会搬过去，它会消失**——因为它不是一个东西，
> 而是**六种职责焊在一起**：入站适配 + 出站适配 + 控制台服务 + 安全关卡 + 定时器 + 状态读写。

**嵌合的核心动作，就是把这六种职责拆开，各自归位。**

## 2. `bridge.js` 的六种职责，各自去哪

| # | 旧职责 | 新家 | 怎么嵌 |
| --- | --- | --- | --- |
| 1 | **入站**：SnowLuma WS → 14 道闸 → 入库 → 唤醒 → 拼提示词 → DSH | **QQ 适配器（上行）+ 内核 K1/K3/K5/K6** | 适配器只把"事件"报上去；全部闸门与判断搬进内核 |
| 2 | **出站**：工具调用 → 闸门 → `onebotSend` → SnowLuma HTTP | **QQ 适配器（下行 `deliver`）** | 适配器只负责"发出去 + 回执"；闸门搬进内核 |
| 3 | **控制台 180 条路由** | **内核管理 API（K8 设置渲染 + K10 管家 + K11 审计）** | 见 §5 待拍板 |
| 4 | **安全关卡**（Host / 令牌 / `x-agent-call` / CSRF） | **内核管理 API 的入口关卡** | 原样保留（这四道闸写得很好，一字不改） |
| 5 | **定时器**（目的 tick / 问候 / 补历史 / 额度 / 心跳） | **内核心跳 + 适配器生命** | 内核有自己的 tick；适配器只报"我还活着" |
| 6 | **状态读写**（`state/` 与 `~/.dsh/surfcore/` 两套根） | **内核状态 + 各适配器子目录** | 见 §5 待拍板 |

## 4. 工具面怎么嵌（这是最关键的一处）

旧架构：**模型调 `qq_send_message` → MCP → 桥接控制台 HTTP → 桥接直接发**。
也就是说"工具"同时是**她的意图**和**执行通道**。

新架构必须拆成两段：

```text
   模型调工具                     内核                       适配器
  ┌──────────┐     ┌────────────────────────────┐     ┌──────────────┐
  │ qq_send_  │────►│ K6 表达器：把工具调用         │────►│ deliver()    │
  │ message   │     │ ① 过闸门（白名单/额度/敏感）  │     │ 真的发出去    │
  │ (MCP)     │     │ ② 变成「意图」               │     │              │
  └──────────┘     │ ③ 记账、审计                 │     └──────┬───────┘
                   └────────────────────────────┘            │
                              ▲                               │
                              └───────── 回执 ────────────────┘
```

**三个不变**：
1. **模型还是调工具**（行为不变，preset 不用改）——所以这次迁移**不需要重训她的习惯**。
2. **闸门全部搬进内核**（白名单/额度/敏感/长度检查）——适配器不再做安全判断。
3. **执行落到适配器**——所以"发消息"这件事第一次有了统一的收口点。

**一句话**：**工具 = 表达器的输入，不是第二条通道。**

## 6. 旧代码里**没有**、必须新建的四样

| # | 新东西 | 为什么旧代码没有 | 优先级 |
| --- | --- | --- | --- |
| 1 | **记录身份 + 可见性**（一条记忆两件事：从哪来 / 给谁看） | 旧代码用 8 字段 3 表示法硬拼（`visibleFor` 53 行） | **最高：挡在入库层前面** |
| 2 | **媒体库**（原件落盘 + 指纹去重 + 引用计数 + 保留期） | 旧代码只有进程内 Map（`messageMediaStore`），**一行落盘都没有** | 高（记忆的 `remember` 依赖它） |
| 3 | **内核心跳**（遗忘/衰减/目的排程由自己驱动） | 旧的是插件每 10 分钟从外面调 | 中（先能手动触发也行） |
| 4 | **适配器管家 + 注册表**（替代 `extensions/` + `platforms/` 两套） | 旧的两套并存，其中一套是空壳 | 中（接第二个渠道前必须有） |

## 7. 嵌合顺序（与迁移计划对齐，只看"嵌"的动作）

```text
第 1 步  终端适配器 + 最小内核     ← 先证明"内核不认识渠道"
第 2 步  记录身份 + 可见性         ← 新建 #1，纯形状 + 政策表
第 3 步  入库层 + 统一读取接口      ← 记忆的地基
第 4 步  叙事读取器（照搬 16 条行为）
第 5 步  向量读取器（主路径）
第 6 步  目的机制接到读取接口
第 7 步  QQ 适配器（工具面 → K6 → deliver）
第 8 步  语音能力包 / 桌宠 / B站
第 9 步  运维层
第 10 步 每一块搬完 → 删旧路
```

## 8. 三个必须你拍板的硬问题

### 问题 1：工具面要不要保留"模型直接调工具"？

| 选项 | 好处 | 坏处 |
| --- | --- | --- |
| **A. 保留**（我建议）：模型照旧调工具，但执行改走"内核→意图→适配器" | 她的行为不变；preset/工具面不用重做；迁移能对拍 | 工具表里的"渠道专属"部分（`qq_*`）将来要考虑改名 |
| B. 改写：模型不再直接有"发消息"工具，只说"想做什么" | 更干净 | **要改 preset + 她的习惯全变**，风险极大 |

**我建议 A**：**先保住行为，再谈净化**。

### 问题 2：控制台那 180 条路由，算"内核的"还是"某渠道的"？

- 里面混着：全局设置、记忆管理、角色管理、表情、语音、B站、桌宠、审计……
- **我的建议**：**内核只保留一套"管理 API"**（设置渲染 K8 + 管家 K10 + 审计 K11）；
  渠道专属的设置**由适配器交菜单、内核统一画**（这正是"菜单"那一块存在的理由）。

### 问题 3：两套状态根要不要合并？

旧的有 `<仓库>/state/`（桥接）和 `~/.dsh/surfcore/`（插件）——这是最容易记混的地方。

- **我的建议**：**新架构只保留一套根**：内核自己一份，每个适配器一个子目录。
- 理由：**两套根的存在理由（两个进程各自拥有）在新架构里消失了**——因为内核与适配器是"契约关系"，不是"两个都拥有数据"。
