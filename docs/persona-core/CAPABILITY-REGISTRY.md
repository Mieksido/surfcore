# 能力清单与清单式治理

> 一句话：**能力清单是系统唯一承认的"能力目录"。适配器只能从里面挑，内核只按声明办事。**
> 它是契约的配套件——契约说"怎么说话"，清单说"**谁被允许做什么**"。
> 立文：2026-11-09。配套：[设计准则](DESIGN-PRINCIPLES.md) · [适配器接口 v0.2](ADAPTER-INTERFACE.md) · [两侧展开](ARCHITECTURE-FROM-CONTRACT.md)

---

## 0. 为什么要"清单式管理"（三条实测缺陷）

查代码得到的现状，正是需要清单的理由：

| # | 现状（实测） | 后果 |
| --- | --- | --- |
| 1 | 扩展的 `capabilities` 是**自由字符串数组**，只做 `map(String).slice(0,20)`（`extensions.js:38`） | 谁都能写任何词；写错、拼错、乱写都"合法" |
| 2 | 这份声明**从不参与任何行为判断** | 声明是装饰品：说"我能改配置"，内核也不会因此多给或少给权限 |
| 3 | `platforms.js:40-42` 反而做对了——按 `PLATFORM_CAPABILITIES` 过滤 | 同一个仓库里，一处校验、一处不校验 = 两套规矩 |

**结论**：能力必须从"文案"变成"**可校验、可授权、可审计的治理依据**"。

## 0.5 最重要的修正：清单是「目录」，不是「闸门」

> 2026-11-09 用户指出：把能力定义得那么具体，等于预设了未来；写抽象接口的目的是**可添加性**。
> 这一条推翻了本文初稿的一个根本错误，记在此处以免后人再犯。

**旧做法（错）**：契约里列 15 + 11 项能力，校验时**必须命中清单**。
后果：**每加一个新渠道、新能力，都要改契约** —— 这正是"不可添加"。
而且它隐含一个不可能的前提：*"我现在就知道你以后要接什么。"*

**新做法（对）**：契约只规定**"一条能力怎么写"**（形状固定），不规定**"有哪些"**（条目开放）。
清单从"准入闸门"降级为**目录**：它会越来越长，但不该拦人。

### 分界原则

> **闭的是"内核的语言"，开的是"外部的声音"。**

| | 开放 / 封闭 | 为什么 |
| --- | --- | --- |
| **渠道能力** | **开** | 外部能声明任何东西；内核只对"认识的那部分"改变行为，其余记录+忽略。加新渠道**不用改契约** |
| **事件** | **开** | 同上。第三方用命名空间自己造（`douyin.gift.sent`） |
| **意图** | **闭** | 意图是内核"要说的话"，它只会说会的几句。渠道特有动作交给 `act`（动作名适配器自定） |
| **权限（授权能力）** | **闭** | 内核不理解一个权限，就无法约束它 → **不认识就不给**（fail-closed） |
| **写法（形状）** | **固定** | 一条能力 = 编号 + 参数；一条事件 = 编号 + 信封。形状不稳，忽略就不安全 |

**一句话记住**：加**渠道**不改契约，加**内核词汇**才改契约。

## 1. 关键区分：两类能力不能混

这是整份清单最重要的设计：

| | **A. 渠道能力（物理）** | **B. 授权能力（信任）** |
| --- | --- | --- |
| 回答的问题 | 这个渠道**物理上能做什么** | 这个扩展**被允许做什么** |
| 例子 | 能发多少字、能不能撤回、多快回音 | 能不能读记忆、改配置、控制桥接 |
| 谁决定 | 客观事实（改不了） | 用户授权（可关） |
| 内核怎么用 | 用来**决定怎么表达**（裁剪、换格式） | 用来**决定放不放行** |
| 缺了怎么办 | 优雅降级（发不了图就只发文字） | 直接拒绝（没授权就不做） |

**为什么必须分开**：混在一起会导致两种事故——
- 把物理能力当授权用 → 用户以为"关掉发图"能限制权限，其实只是限制功能；
- 把授权能力当物理用 → 内核以为"没有这个能力"就降级，而实际是"没被允许"，应该报错而不是降级。

## 2. 目录 A：渠道能力（物理，适配器声明）

> ⚠️ **下表是"内核当前认识的"，不是"允许声明的"。**
> 不在表里的能力**不算错**：适配器照样可以声明，内核只是不据此改变行为。
> 要不要把它加进下表，取决于**内核是否需要因它改变行为**——那是内核升级，不是适配器的事。

| 编号 | 人话 | 参数 | 缺省时内核怎么办 |
| --- | --- | --- | --- |
| `text.send` | 能发文字 | 最多字数、是否支持粗体/链接/@/引用 | 不能发文字 → 只能发媒体或动作 |
| `text.recall` | 能撤回 | 时限 | 不能撤回 → 说出的话不可收回，表达更保守 |
| `text.edit` | 能编辑 | 时限 | — |
| `media.image` | 能发图 | 单张上限 | 不能发图 → 用文字描述代替 |
| `media.voice` | 能发语音 | 时长上限 | 不能发语音 → 转文字 |
| `media.video` | 能发视频 | 大小上限 | 不能发视频 → 发链接或摘要 |
| `media.sticker` | 能发表情 | — | 不发 |
| `action.execute` | 能执行动作（游戏/世界指令） | 动作名由适配器自定 | 不能动作 → 只说话不做 |
| `stream.out` | 能流式输出（边说边发） | — | 改一次性整段 |
| `stream.in` | 能流式输入（连续听） | — | 改一条一条 |
| `bargeIn` | 能被抢话 | — | 不发 `cancel` |
| `read.receipt` | 有已读回执 | — | 不假设对方看过 |
| `presence` | 有上下线事件 | — | 不判"在不在线" |
| `identity.actor` | 能识别说话人 | — | 只能说"有人说话" |
| `anonymous` | **可能没有身份** | — | 缺失时必须允许"说话人为空"，否则崩 |

> 注意 `anonymous` 不是"能力"，是"**可能会缺**"的声明。它必须显式声明，因为内核默认假设"总有个人"。

## 3. 清单 B：授权能力（信任，用户可关）

| 编号 | 人话 | 风险 | 默认 | 用户可关 | 内核放行条件 |
| --- | --- | --- | --- | --- | --- |
| `event.publish` | 上报事件 | 低 | ✅ 开 | 可 | 总是允许（这是它的本职） |
| `route.publish` | 注册自定义 HTTP 路由 | 中 | 关 | 可 | 需显式授权 |
| `config.read.own` | 读**自己的**配置 | 低 | ✅ 开 | 可 | 总是 |
| `config.write.own` | 写自己的配置 | 低 | ✅ 开 | 可 | 总是 |
| `config.write.global` | 改**全局**配置 | **高** | 关 | 可 | 单独授权 + 审计 |
| `memory.read.public` | 读公开档（自我简介一类） | 低 | 关 | 可 | 单独授权 |
| `memory.read.scoped` | 读"该渠道可见"的记忆 | **中** | 关 | 可 | 单独授权 + 审计 |
| `memory.write.candidate` | 提交记忆候选 | 低 | ✅ 开 | 可 | 总是（内核决定收不收） |
| `align.write` | 改身份对齐 | **高** | 关 | 可 | 单独授权 + 审计 |
| `bridge.control` | 控制桥接（启停/发消息） | **极高** | 关 | 可 | 单独授权 + 审计，且需二次确认 |
| `network.out` | 对外网络访问 | **中** | 视用途 | 可 | 声明用途后授权 |
| `fs.local` | 本地文件读写 | **极高** | 关 | ❌ 不建议 | 默认不提供；需要则走子进程+白名单 |
| `spawn.process` | 起子进程 | **极高** | 关 | ❌ 不建议 | 同上 |

**三条硬规矩**：
1. **高频低危默认开**（上报事件、自己的配置），这样普通扩展"装上就能用"。
2. **高危默认关且单独授权**，界面上必须写清"这意味着什么"（不是勾选框，是人话）。
3. `fs.local` / `spawn.process` **不通过授权提供**——真要这类能力，宁可走"受管子进程 + 目录白名单"，这是另一套机制，不混进能力清单。

## 4. 清单 C：禁止项（不是能力，永远不许）

有些事**不是"能力开关"，是绝对禁止**。它们不该出现在清单里，而该出现在"禁止清单"里：

| 禁止项 | 为什么不是能力 |
| --- | --- |
| 伪造事件来源（自称别的适配器） | 这是**欺骗**，不是功能 |
| 绕过发送白名单 | 安全底线（准则 002） |
| 直接读写记忆存储文件 | 破坏单写者（准则 007） |
| 自己画设置界面 | 钓鱼风险（准则 003） |
| 替用户做"关掉安全校验"的决定 | 安全底线 |

> **判据**：能被"授权"的叫能力；**只有"允许/不允许"、不许授权给第三方的叫禁止项**。
> 把禁止项写成能力，等于给了一把拆刹车的钥匙。

## 5. 校验与协商规则

### 5.1 注册时：只查形状，不查点名

1. **真错只有四种**：结构不对（缺字段）、编号格式不合法（不是 2~3 段小写点号）、协议版本不符、出现禁止项。
2. **未知渠道能力 → 不算错**。记进"未识别"，界面可显示，内核不据此改变行为。
3. **未知事件 → 不算错**。内核忽略但记审计（前向兼容的唯一办法）。
4. **未知意图 → 警告，不算错**。因为意图是内核的语言，适配器声明了内核也不会发——这是"声明与能力不匹配"的信号。
5. **未知授权能力 → 不算错，但绝不授予**（fail-closed）。内核不理解一个权限，就无法约束它。
6. **编号规则**：2~3 段小写点号（`text.send` / `douyin.gift` / `douyin.gift.sent`）。
   规则的意义不是拦人，而是**让"不认识的东西"也有规矩**，这样内核才能安全地忽略它。

> 这六条的不对称是刻意的：**放开"外部的声音"，守住"内核的语言"。**

### 5.2 用户授权时（可见、可撤）

3. 每个高危能力在界面上是**一句话 + 后果**，例如：
   > 「**读取她在本群范围内的记忆**——能让她在该群聊得更像本人；也可能把别处的事带进这个群。可以随时关。」
4. 授权**可随时撤销**，撤销后立即生效（不必重启）。
5. 撤销时，内核要**清理**该能力留下的东西（卸载清单的一部分）。

### 5.3 运行期（每次都查）

6. **不能只在启动时查一次**。每次使用高危能力都要过检查并**记审计**（谁、何时、什么能力、结果）。
7. 用户关掉某个渠道能力后，内核**立刻**改为降级表达（不需要重启适配器）。

## 6. 清单驱动什么（这才叫"依照清单管理"）

| 被驱动的东西 | 怎么被驱动 |
| --- | --- |
| **权限** | 清单 B 决定放行/拒绝；禁止清单永不通过 |
| **表达** | 清单 A 决定裁剪与降级（不能发图 → 转文字） |
| **界面** | 高危能力生成授权卡片；能力变化 → 界面自动更新 |
| **测试** | **清单即测试矩阵**：每个能力必须有两个用例——"声明了能用" + "没声明能优雅降级" |
| **文档** | 清单是唯一权威；其他文档只引用编号，不再各自描述 |
| **更新/退役** | 内核不支持某能力时要通知适配器；能力退役要走版本规则（只加不改） |
| **审计** | 高危能力的使用必须留痕，可按能力检索"谁用过" |

### 最有价值的一条：清单即测试矩阵

现在的问题是"新增一个能力 = 没人知道要测什么"。清单化之后：

```text
每个能力 → 2 条测试（能 / 不能）
         → 1 条授权测试（高危：关掉时必须拒绝而不是降级）
```

这样"能力清单"和"测试覆盖"就永远对得上——**这是最容易腐烂的地方，用清单钉死**。

## 8. 迁移（从"自由字符串"到"清单治理"）

1. **先立清单**（本文 §2/§3），冻结编号——编号一旦发布不再改含义。
2. **加校验，先只警告**：未知能力回告但不拒绝，观察现有 2 个扩展是否有非法声明。
3. **加授权**：把高危 API（memory/bridge/align）从"直接注入"改成"按能力注入"，默认关。
4. **加测试矩阵**：每个能力两条用例，进 `test:audit`。
5. **加审计**：高危使用留痕。
6. **删旧路**：旧的"全量注入"必须删掉，不许并存（准则 000 第 3 条）。
