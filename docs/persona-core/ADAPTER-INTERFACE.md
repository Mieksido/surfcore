# 适配器接口 v0.2（一证、六表、三管）

> 人格内核与外部世界之间的全部约定。不写代码，只写"谁给谁什么、坏了怎么办"——
> **不懂代码的人也能逐条评审**。
> 配套：[设计准则](DESIGN-PRINCIPLES.md)（为什么）· 本文（是什么）
>
> **版本**：v0.2（2026-11-09）　**协议版本**：`1`
> **状态**：骨架已冻结，字段在 v0.x 期间可变。
>
> v0.2 相对 v0.1 的改动（全部来自 2026-11-09 用户评审）：
> ① 删除"质量等级"（无消费方，纯复杂度）；② 修正"我的世界不能发文字"的错误示例，并加"示例值必须实测"规矩；
> ③ 内容分类改为「感官 × 形态」双轴，新增"结构化状态"感官；④ 新增第六张表：媒体表（原图/原声的存储与引用）；
> ⑤ 明确"存档层 vs 注意力层"两级存储；⑥ 澄清记忆单写者是内核而非适配器；⑦ 明确"共享人格 + 可见性过滤"；
> ⑧ 文档分骨架层/字段层/实验层。

## 0. 骨架（这一层冻结，以后不改）

```text
        ┌──────── ① 上行管：事件 ────────►
适配器   │                                   人格内核
        ◄──────── ② 下行管：意图 ────────┘
        ┌──────── ③ 回执管：结果 ────────►
```

**适配器 = 一张身份证 + 六张表 + 三根管子。**

| 件 | 是什么 |
| --- | --- |
| 一证 | 我是谁（注册时交一次） |
| 表1 能力 | 我能干什么、不能干什么、多快、多频繁 |
| 表2 菜单 | 用户能调什么（我只交单子，界面内核画） |
| 表3 事件 | 我会报什么 |
| 表4 意图 | 我能执行什么 |
| 表5 生命 | 我怎么证明活着、删我时清什么 |
| 表6 媒体 | 我交上来的图/音/视频存在哪、被谁引用 |
| 三管 | 上行事件 / 下行意图 / 上行回执 |

两条铁律（准则 007）：
- **内核不认识渠道名**（不知道"QQ"是什么，只读能力表）；
- **适配器不认识记忆**（读不到她的日记，只能提交候选）。

## 1. 一证：身份证

| 字段 | 人话 | 例子 | 必需 |
| --- | --- | --- | --- |
| 编号 | 全局唯一；**内核用它给上报盖章**（防冒充） | `qq` / `mc-server-7` / `douyin` | ✅ |
| 显示名 | 给人看的 | "QQ" / "我的世界服务器" | ✅ |
| 适配器版本 | 你这版的版本 | `1.4.0` | ✅ |
| **协议版本** | 我们说的是第几版规矩 | `1` | ✅ |
| 类别 | 聊天 / 世界 / 游戏 / 传感器 / 只读屏 | `chat` | 建议 |

- **类别只给人看**，内核行为不许据它分支。
- ~~质量等级~~ **已删除**：它现在没有任何消费方（没有界面显示、没有校验规则、没有按它分流的逻辑）。等真有几十个适配器、用户挑不过来时再加，届时按准则 005 记账（新增字段=新增测试与界面成本）。

## 2. 表 1：能力表（我能干什么）

**整套结构的枢纽。** 所有渠道差异压进这张表，内核只读它、永不读你的名字。

### ① 发

| 字段 | 人话 |
| --- | --- |
| 文字 | 能发吗、最多几字、是否支持粗体/链接/@人/撤回/编辑 |
| 媒体 | 能发图/语音/视频/表情吗、单个多大、一次几个 |
| 动作 | 能执行世界指令吗、有哪些（**名字由适配器自定，内核不枚举**） |

### ② 收
能收到哪些「感官 × 形态」组合（见 §3.2）。

### ③ 快慢

| 字段 | 人话 |
| --- | --- |
| 签收期限 | 发出去后多久内必须给回执（毫秒），超时内核判失败 |
| 同步预算 | 最急情况给内核多少时间（回合制游戏可能只有 200 毫秒） |
| 典型延迟 | 正常多久送到（用于预判体验） |

### ④ 频率
每分钟条数、突发上限、并发上限。

### ⑤ 特殊能力与边界（攻击测试逼出来的，别删）

| 字段 | 人话 | 为什么必须有 |
| --- | --- | --- |
| 能撤回 / 能编辑 / 有已读回执 | 有就说有 | 没有时内核不许要求 |
| 支持流式 | 实时语音/直播，内容是连续流 | 决定用「单体」还是「流」 |
| 能被抢话 | 打电话能打断 | 决定要不要发 `cancel` |
| 刷新延迟 | 电子墨水屏 10 秒才变 | 影响内核节奏预期 |
| **可能没有身份** | 匿名渠道（传真、匿名投稿） | 否则内核假设"总有个人"，在匿名渠道上崩 |
| 单次收支上限 | 张数 + 总大小 | 适配器侧物理上限（用户调档只能更低） |

> **示例值必须实测，不得凭印象填。**
> v0.1 曾错误地写"我的世界不能发文字"——实际上玩家在局内聊天栏就能打字。
> 教训：能力表的价值正是把"能不能发文字"这种是非题变成具体参数（MC 是"短、纯文本、聊天栏、无 @、无图"）。

## 3. 表 3 前置：内容的两个轴（§3.2 展开）

内容不能只按"消息"想。用**两个轴**描述一切内容：

### 3.1 感官轴（这是什么性质的东西）

| 感官 | 含什么 | 例子 |
| --- | --- | --- |
| **视觉** | 文字、图像 | 群消息、截图、表情包 |
| **听觉** | 音频、以及音频的转写文字 | 语音条、电话、直播 |
| **结构化状态** | 非视听的数据 | 血量、坐标、手牌、库存、金币 |

> 第三类必须存在：游戏状态既不是给眼睛看的也不是给耳朵听的，它是**给机器读的数据**。
> 硬塞进"视觉"会让内核以为那是一张图。

### 3.2 形态轴（这是怎么传的）

| 形态 | 说明 | 例子 |
| --- | --- | --- |
| **单体** | 一次一条，有始有终 | 一条群消息 |
| **流** | 连续片段，可被取消 | 电话、直播 |
| **快照** | 当前完整状态 | 游戏局面、背包 |
| **摘要** | 人话一句 + 关键数字 | "血 12/80，刚打完一群史莱姆" |

**两轴交叉能描述一切**：群消息=视觉×单体；语音条=听觉×单体；电话=听觉×流；血量=结构化×快照；战报=视觉文字×摘要。

## 4. 表 2：菜单表（用户能改什么）

每个选项**七件事**：键、显示名、说明、默认值、可选值、**代价**、分组（基础/高级/实验）。

| 项 | 例子 |
| --- | --- |
| 键 | `video.frames` |
| 显示名 | 视频精细度 |
| 说明 | 每次视频取几张关键画面 |
| 默认值 | 6 帧 |
| 可选值 | 3 帧 / 6 帧 / 逐秒 |
| **代价** | 越细越贵越慢；3 帧最省，但可能漏细节 |
| 分组 | 高级（默认折叠） |

三条硬规矩（准则 001/002/003/005）：
1. 菜单**只放用户偏好**；"关掉会出事故"的（关白名单、关令牌检查）**不许做成开关**。
2. **界面由内核统一画，配置存在内核**（能导出/备份/换机）。适配器只交单子，不许自己画——否则能伪造登录框钓鱼。
3. 每加一个开关，记一笔测试账。

## 5. 表 3：事件表（我会上报什么）

### 固定事件（内核认识）

| 事件 | 什么时候 | 频率 |
| --- | --- | --- |
| `message.received` | 有人说话 | 人类速度 |
| `message.recalled` | 撤回 | 低 |
| `presence.changed` | 上线/离线/进群/退群 | 低 |
| `stream.chunk` | 流式内容片段 | 高 |
| `world.tick` | 世界推进 | **很高**（每秒多次） |
| `world.digest` | 世界摘要（人话） | **低**（关键事件 + 定时兜底） |
| `action.result` | 上一个动作的结果 | 中 |
| `decision.requested` | 请求内核决策 | **极低**（必须限频） |
| `adapter.health` | 心跳/健康 | 定时 |

### 自定义事件
必须带命名空间：`douyin.gift.sent`、`sts2.card.drawn`。
**内核规则：不认识的类型 → 安静忽略 + 记一行审计，绝不报错、绝不崩。**

## 6. 表 4：意图表（我能执行什么）

| 意图 | 意思 | 必需 |
| --- | --- | --- |
| `say` | 说一句话 | ✅ |
| `send_media` | 发图/语音/视频/表情 | 有能力则支持 |

| `ask` | 提问并等回答 | 建议 |

## 8. 表 6：媒体表（原图/原声怎么存）

**记忆里存文字描述，原件另存，用"媒体编号"关联。**（用户 2026-11-09 提出，采纳）

| 字段 | 人话 |
| --- | --- |
| 媒体编号 | 唯一 id（**这是身份，路径不是**） |
| 种类 | 图 / 音频 / 视频 / 文件 |
| **内容指纹** | 内容哈希：同一张图被转发十次只存一份；也能校验损坏 |
| 存储路径 | 当前存放位置（可以变，不是身份） |
| 大小 / 尺寸 / 时长 | 用于配额与展示 |
| 谁交的 | 来源适配器 + 渠道 + 时间 |
| **被谁引用** | 哪些记忆条目引用了它 |
| 保留期 | 到期后只留摘要与关键帧 |

四条必须处理的规则：

1. **删记忆不立刻删文件**：记忆条目只是"引用"；删到最后一条引用，才删文件（否则会删掉别人还在用的图）。
2. **路径会失效**：文件可能被移动/改名。所以**用媒体编号 + 内容指纹做身份**，路径只是"现在在哪"。
3. **描述会丢信息**：记忆里存文字描述，但允许"回看原件"。描述分两级——适配器给粗描述（便宜），内核需要细看时再看原件。
4. **会无限膨胀**：必须有配额 + 保留期（例如原始视频 7 天后只留摘要和 3 张关键帧）。

**媒体一律"传替身，不传原件"**（准则 006）：
- 图像 → 缩略图（长边压到 1024 内）+ 一句说明
- 音频 → 文字稿 + 语气线索 + 媒体编号
- 视频 → **3~8 张关键画面 + 文字稿 + 时长** + 媒体编号
- 需要原件时，凭媒体编号向内核申请（**适配器不承诺"以后还能取"**，很多平台链接有时效）

## 9. 三根管子

### 9.1 上行：事件信封

| 字段 | 人话 | 可空 |
| --- | --- | --- |
| 事件类型 | 这是什么 | ❌ |
| 渠道 | 哪个会话/频道/世界 | ❌ |
| **说话人** | 谁 | ✅ **可空**（匿名渠道） |
| 时间 | 什么时候 | ✅（空则用内核时间） |
| **编号** | 这条的身份证 | ✅ **可空**（流式内容没有"一条"） |
| 内容 | 感官 × 形态 × 替身/原件引用 | ❌ |
| 因果（可选） | 在回哪一条 / 属于哪条流 | ✅ |

- 两个"可空"必须显式允许：不允许空，内核就会假设"总有个人、总有编号"，在匿名渠道和流式语音上崩。
- **来源由内核盖章**，不接受适配器自报（准则 009）。

### 9.2 下行：意图
每条带：**唯一编号**（防重复）+ 目标渠道 + 内容 + 期限。
**适配器必须幂等**：同一编号收到两次，只许执行一次。

### 9.3 回执：五种结果

| 结果 | 人话 | 内核怎么办 |
| --- | --- | --- |
| 成功 | 送到了 | 记账 |
| 失败 | 出错了 | 重试 / 告诉用户 |
| 做不到 | 我没这能力 | 换个表达 |
| 被限流 | 太频繁 | 排队 |
| **已发出、无法确认** | 像传真：交出去了，不知道对方收没收到 | **既不算成功也不算失败**，按尽力而为记账并如实告知 |

第五种必须有：短信、邮件、广播、传真都属于这类。**少这一种，系统就会说谎。**

## 10. 记忆：两级存储 + 单写者

### 10.1 两级（准则 008 的落地）

| 层 | 存什么 | 能不能"一切都存" | 进不进她的提示词 |
| --- | --- | --- | --- |
| **存档层** | 原始事件、原始描述、媒体引用（只追加，不修改） | ✅ 可以，而且应该 | ❌ 不进 |
| **注意力层** | 筛过、压过、带衰减的记忆卡 | ❌ 不行（会撑爆上下文、烧钱） | ✅ 进 |

**高频事件例外**：`world.tick` 每秒多次，**不能一切都存**（会写爆磁盘）。
这类必须由适配器先压成 `world.digest` 摘要——谁更懂谁过滤（准则 006）。

### 10.2 单写者（对 v0.1 的澄清）

- **记忆的写者只有一个：内核。** 适配器只能交候选（`remember`）。
- 多个适配器可以**同时灌**，但**写进记忆的只有内核一个入口，内核内部排队**。
- 所以"多平台不会双写"的正确理由是：**记忆只有一个入口**，
  而不是"适配器是单写者"（适配器只是"只写自己那一段渠道数据"）。

### 10.3 共享人格 + 可见性过滤（准则 007）

- **同一份人格 + 同一份记忆库**：所以她在 QQ、B站、游戏里是同一个人。
- **共享 ≠ 全部可见**：每条记忆带来源与可见范围；每个渠道只能看到她"该在那个地方知道的事"。
- 反例（必须防住）：在 B站 公开评论区引用 QQ 私聊里的内容。
  现有代码有专门的隐私评分与范围过滤来防这个，新架构必须保留。

## 11. 三方义务

| 内核保证 | 适配器保证 |
| --- | --- |
| 回执在签收期限内到，否则判失败 | 启动成功后上报；停止后不上报 |
| 同一意图编号不重复执行 | 同编号收到两次只做一次 |
| 按声明频率发送，绝不超 | 不伪造来源、不声称未声明的能力 |
| **不认识的事件安静忽略** | 超频时接受削峰 |
| **裁剪时必须告知用户** | 卸载时清干净 |

| 内核**不**保证 | 适配器要知道 |
| --- | --- |
| 顺序 | 多渠道天然并发 |
| 端到端送达 | 回执只代表"平台收下了" |
| 文本格式 | 渲染归适配器 |

## 12. 版本演进规则（让"错了好改"）

1. **只加不改**：加字段可以，改已有字段含义不行。
2. **不认识就忽略**：双方都要容忍新字段/新事件。
3. **协议版本必须带**：内核据此区别对待老适配器。
4. **接口可退役**：老版本至少保留一个大版本，并提前告示。

## 15. 契合 SurfCore 的四件职责

| 内核职责 | 适配器结构里的落点 |
| --- | --- |
| **身份** | 身份证（编号→盖来源戳）+ 信封（说话人，可为空） |

## 17. 与现有代码的对照（2026-11-09 实测，`dev@856e924`）

> 写完 §0–§16 之后才查的代码，**下面四条修正了契约的前提**。

### 17.1 已经存在、应当演进而非重造

| 已存在 | 位置 | 关键点 |
| --- | --- | --- |
| **扩展宿主 `ExtensionHost`** | `plugins/surfcore/lib/extensions.js`（287 行） | `extensions/<id>/manifest.json` + `entry`；**默认关闭**；装配有 disposer 链（停用反向释放）；**配置集中存在插件侧** `extensions.json` 的 `config[id]`；有事件总线 `on/emit`；有自定义路由 `registerRoute`/`routeFor`；可 `registerPlatform(adapter)` |
| **平台注册表** | `plugins/surfcore/lib/platforms.js`（165 行） | 适配器接口 + `register()` 返回 disposer + **内置不可覆盖** + `loadLocal()` 从 `platforms/*/manifest.json` 动态载入 |

### 17.2 四条必须先纠正的事实（与 v0.2 的前提冲突）

| # | 实测事实 | 对契约的影响 |
| --- | --- | --- |
| 1 | 扩展是**同进程动态 `import()`**（`extensions.js:139`），拿不到沙箱，拥有完整文件/网络/进程权限 | 准则 010「适配器一律不可信」**在当前实现下做不到**。v1 只能做到：默认关闭 + 显式开启 + 安全提示 + 收窄 API |
| 2 | 扩展拿到 `api.memory`、`api.bridge`、`api.align` 三个**完整服务对象**（`extensions.js:217-219`） | 权限比"读记忆"更宽——它能直接控制桥接、改对齐状态。这与准则 010 冲突最重 |
| 3 | `capabilities` 是**自由字符串**，从不校验（`extensions.js:38` 只做 `map(String).slice(0,20)`），也不据此限制任何行为 | 能力声明目前是**装饰性的**。对比 `platforms.js:40-42` 会按 `PLATFORM_CAPABILITIES` 过滤——那里做对了 |
| 4 | 平台适配器那套（`platforms/`）下**只有 `tieba/manifest.json`，没有 index.js** | 这套"平台适配器"机制**从未真正用于任何平台**；业务仍硬编码 qq/bili（上轮实测 61 处）。**两套接入机制并存** |

### 17.3 媒体存储：这是全新能力，不是重复设计

实测：

- `messageMediaStore` 是 bridge 进程内的 `new Map()`（`src/bridge.js:10920`），每会话上限 500（`:10119`），在会话切换/清空多处 `clear()`——**没有任何落盘代码**。
- `state/` 下 32 个文件中没有任何媒体文件（上一轮实测清单）。
- 插件侧 `lib/memory-card.js`、`lib/memory.js` 里 `media`/`image`/`audio` **一个都搜不到**——记忆层是纯文本。
- 向量记忆也是纯文本。

**结论**：用户要求的"图片/音频另存 + 记忆只存文字描述和媒体编号"是**要新建的基础设施**。
§8 的媒体表正好是它的契约；但它需要配套：新存储根、内容指纹去重、引用计数、保留期。

### 17.4 建议（按优先级）

1. **合并两套接入机制**：`ExtensionHost` 作为唯一宿主；`platforms/` 降级为"扩展的一种能力"。
   两套 manifest 形状、两套加载器、两套注册路径 = 必有一整套长期没人维护（现状已证明：platforms 那套是空壳）。
2. **把扩展 API 从"给对象"改成"给能力"**：`memory`/`bridge`/`align` 改为"manifest 声明 + 用户同意才注入"。
   这是当前最大的权限缺口（17.2 第 2 条）。
3. **`capabilities` 必须白名单校验**：照抄 `platforms.js:40-42` 的做法（按已知能力集过滤），并**据此真正限制行为**。
4. **配置 UI 从 JSON 文本框升级为声明式表单**：这正是 §4 菜单表的落点，也是用户体验上最明显的一处缺口——
   现在让用户手写 JSON 来配置扩展，等于把"配置"这件事推给了会写 JSON 的人。
5. **新建媒体存储**：`media/` 根 + 内容指纹去重 + 引用计数 + 保留期；记忆只存"描述 + 媒体编号"（§8）。
6. **信任分级写进文档**：内置 / 本地样例 / 第三方；并**诚实写明 v1 无沙箱**——不要在设计文档里承诺做不到的隔离。

### 17.5 准则 010 需要修订（待用户确认）

现文写着"适配器一律不可信：默认拒绝、最小权限、可审计、卸载不留孤儿"。
按 17.2 第 1 条，**同进程 import 无法做到真正的不可信**。建议改写为：

> **准则 010（修订版）· 适配器按信任分级管理**
> ① 默认关闭，用户显式开启才运行（已实现）；
> ② 能力必须白名单校验，并按声明注入（当前缺失）；
> ③ 高危能力（改桥接、读全量记忆）必须单独授权并在界面标注；
> ④ v1 无沙箱：同进程运行，因此**只允许用户信任的扩展**——这一条必须如实写在文档与界面上，不许含糊；
> ⑤ 卸载不留孤儿（已实现）。
