# 以契约为中心，往两边展开

> 这份文档回答一个问题：**有了适配器契约（v0.2）之后，内核和扩展两边分别长什么样？**
> 它与 [ADAPTER-INTERFACE.md](ADAPTER-INTERFACE.md) 配套：那份是"中间那条线"，这份是"两边的房子"。
> 立文：2026-11-09。依据：`dev@856e924` 的实测代码 + 用户的三条决定。
>
> **本文遵守一条修订规则**（用户 2026-11-09 要求）：
> 每次推翻或修正，必须写清「旧结论 → 为什么错 → 新结论」。只给结论不算。

---

## 0. 先纠正一次方法论（这决定了后面所有事）

### 旧结论（2026-11-09 上午）
"扩展宿主 `ExtensionHost` 已经存在且写了 287 行，契约应该长在它上面，不要重复造。"

### 为什么错

1. **那是代码复用，不是架构判断。** 存在的东西不等于值得当基础。
2. **它带着一个错误的根假设**：把 `memory`、`bridge`、`align` 三个完整服务对象直接递给第三方扩展
   （`extensions.js:217-219`），等于"扩展是自己人"。以它为基础 = 继承"自己人"假设。
3. **它会诱导"两套机制长期并存"**：`extensions/` 与 `platforms/` 本来就是两套（后者是空壳），
   一旦把契约挂到其中一套上，另一套更难拆。

### 新结论
**契约是中心，内核与扩展各自按契约重新生长；旧代码只当参考资料（需求来源），不当骨架。**

> 这条已升格为宪法：[准则 000（元准则）· 旧架构是「需求」，不是「骨架」](DESIGN-PRINCIPLES.md)。
> 本文 §5「功能不丢」表就是它的执行工具：**旧代码只用来回答"什么不能丢"**。

### 风险与对策（这一条必须写，否则"干净"会变成"失忆"）

旧代码里有一批**用事故换来的规则**（EPERM 锁死、只读降级假成功、沉睡观察、令牌拒发、四把钥匙…）。
"不用旧架构"**不等于**"忘掉这些教训"。

**对策**：把教训变成**契约字段**或**内核规则**，而不是把旧代码搬过来。
本文 §5 的"功能不丢"表就是这条对策的落地。

## 1. 三种地基，为什么选第二种

| | 以旧代码为地基 | **以契约为中心** | 完全抛弃重写 |
| --- | --- | --- | --- |
| 功能能否保住 | ✅ 基本能 | ✅ 能（按需求重实现） | 🔴 会丢（没人记得全） |
| 紊乱是否遗传 | 🔴 遗传 | ✅ 不遗传 | ✅ 不遗传 |
| 事故教训是否保留 | ✅ 保留 | 🟡 需要显式搬（§5） | 🔴 容易丢 |
| 成本 | 低 | 中 | 高 |
| 权限模型能否修正 | 🔴 难（根假设在） | ✅ 能 | ✅ 能 |
| **结论** | 否 | ✅ **选它** | 否 |

## 3. 内核侧：契约反推出来的部件

内核的部件不是"按功能想出来的"，而是**契约里每一样东西，都必须有人在对面接住**。

| # | 部件 | 由契约的哪部分逼出来 | 一句话职责 | 输入 → 输出 | **不做什么** |
| --- | --- | --- | --- | --- | --- |
| K1 | **事件入口闸** | 上行管 | 校验信封、去重、盖来源戳、丢弃不合法事件 | 原始事件 → 合法事件 | 不解释内容、不做业务判断 |
| K2 | **能力协商台** | 能力表 | 把"渠道物理能力"翻译成"内核这次能做什么" | 能力表 + 用户偏好 → 本次可用的表达方式 | 不缓存成永久配置（能力可变） |
| K3 | **注意力漏斗** | 事件表（尤其 tick/digest） | 决定"这个事件值不值得叫她" | 合法事件 → 要不要唤醒 | 不产生回复、不算钱 |
| K4 | **人格与身份** | 身份证 + 信封(说话人) | 她是谁、在跟谁说话、用什么称呼 | 事件 → 语境（她是谁 / 对方是谁） | 不认识渠道 |
| K5 | **记忆** | 表 6 媒体 + `remember` 意图 | 存什么、忘什么、谁能看见 | 事件/候选 → 记忆条目 + 媒体编号 | 不做表达、不发消息 |
| K6 | **表达器** | 下行管 | 把"想做的事"翻成一个**意图**，并按 K2 裁剪 | 决定 → 意图 | 不直接发消息（只交意图） |
| K7 | **投递账本** | 回执管 | 谁发了什么、结果如何、要不要重试、花了多少钱 | 回执 → 状态 + 账 | 不做语义判断 |
| K8 | **设置渲染器** | 菜单表 | 把各适配器的菜单合成一个统一表单 | 各适配器菜单 → 界面 | 不允许适配器自带界面 |
| K9 | **媒体库** | 表 6 | 存原件、算指纹、去重、引用计数、到期清理 | 媒体替身/原件 → 编号 | 不判断内容含义 |
| K10 | **适配器管家** | 生命表 | 加载/启停/心跳/健康/卸载清场 | 生命周期事件 → 状态 | 不介入业务 |
| K11 | **审计** | 全部（准则 010） | 谁在什么时候做了什么、被谁拒了 | 任意 → 只追加的记录 | 不改任何数据 |
| K12 | **预算** | 能力表 + 回执照 | 能花多少、现在贵不贵、超了先砍谁 | 消耗 → 账 + 闸 | 不设"口味上限"（准则 008） |

### 三条内核铁律（都来自契约，不是我的偏好）

1. **内核不认识渠道名**：只读能力表。任何 `if (渠道 === 'qq')` 都是违约。
2. **内核不联网**：媒体由适配器压好交来；内核不代取任何外部内容。
3. **记忆只有一个写者**：适配器只能提交候选（`remember`），内核串行落库。

### 内核的"四件职责"如何映射到 K 件

| 四件职责 | 由哪些 K 件共同承担 |
| --- | --- |
| 身份 | K4 + K2（称呼/口径随渠道变） |
| 记忆 | K5 + K9 + K1（去重/指纹） |
| 时机 | K3 + K2（延迟/频率）+ K6（`stay_silent` 也是决定） |
| 预算 | K12 + K7 + K9（媒体保留期省钱） |

## 4. 扩展侧：一个适配器作者需要什么

契约规定"必须实现什么"，SDK 规定"你可以少写什么"。两者要分明：

### 4.1 最小实现（必须自己做，无法代劳）

| 必须 | 为什么不能代劳 |
| --- | --- |
| 报身份证 | 只有你知道自己是谁 |
| 报能力表 | 只有你知道那个平台能干什么 |
| 交出菜单声明 | 只有你知道有哪些可调项 |
| 实现"执行意图" | 只有你能真的发出去 |
| 报回执 | 只有你知道平台收没收到 |
| 心跳 | 只有你知道自己还活着 |

### 4.2 SDK 应该代劳的（不该让每个适配器重写一遍）

| 代劳项 | 为什么必须统一做 |
| --- | --- |
| 重试与退避 | 每个适配器各写一套 → 行为不一致、有的无限重试 |
| 限流与削峰 | 同上；而且内核要据此算账 |
| 媒体压缩/抽帧/转写 | 各写一套 → 质量参差、有的忘压缩导致巨额账单 |
| 事件信封的构造与校验 | 少写一个字段就是静默事故 |
| 幂等表 | 防重发必须统一 |
| 日志与脱敏 | 凭据不许进日志（准则红线） |
| 菜单声明的表单定义 | 让"报菜单"变成填空，不是写框架 |

### 4.3 三类适配器的差异（同一契约，不同重点）

| 类型 | 例子 | 重点字段 | 典型坑 |
| --- | --- | --- | --- |
| **聊天型** | QQ、抖音私信 | 文字长度、@、撤回、频率 | 把"多条"发成"一条" |
| **世界型** | 我的世界、直播 | `world.digest`、`decision.requested`、`act`、同步预算 | 每 tick 都上报 → 烧钱 |
| **只读型** | 电子墨水屏、公告牌 | 刷新延迟、无回执或"无法确认" | 让内核以为能"已读" |

## 6. 迁移顺序（三步，避免"两套并存"）

### 第 1 步：立骨架，跑空闭环
- 写 **K1/K6/K7**（事件入口、表达器、投递账本）三个最小件 + **一个假适配器（终端 REPL）**。
- 验收：**"她说 / 她沉默 / 她记住"** 三件事在终端里跑通，且**内核代码里没有任何渠道名**。
- 这一步不碰旧代码，旧系统照常运行。

### 第 2 步：双轨并行，一个真渠道
- 选**一个**真实渠道（建议 QQ，因为它最难：有撤回、@、频率、令牌、白名单），写成新契约下的适配器。
- 内核补齐 K2/K3/K5/K10。
- 验收：**同一个进程里，旧桥接和新适配器都能收发**，且行为一致（用同一批消息对拍）。
- 这一步才开始"啃"旧代码，而且只啃"读"（对照行为），不啃"搬"。

### 第 3 步：删旧路
- 每搬完一个能力，**立刻删掉旧实现**（或隔离到 `_quarantine`），不许留两条路。
- 验收：旧 `bridge.js` 的入站/出站链路被新链路完全替代，且 `test:audit` 全绿。

> **第 3 步的纪律最重要**：不删旧的，"两套并存"就是新紊乱的开始。
