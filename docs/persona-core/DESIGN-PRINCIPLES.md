# 设计准则（人格内核 + 适配器）

> 这份文件是这套系统的**宪法**。任何接口设计、任何新开关、任何适配器行为，先对一遍。
> 每条都写三件事：**准则 / 为什么 / 边界**。
> 边界比准则更重要——因为后人执行准则时，几乎总是往极端方向跑偏。
>
> 立宪日期：2026-11-09（用户口述，逐条确认后成文）
> **配套：[架构法则](ARCHITECTURE-LAWS.md)** —— 管"结构怎么长"（边界、分层、依赖、可测性、适应度函数）。
> 准则是"产品与交互怎么定"，法则是"结构怎么长"；**两者冲突时以法则优先**。
> 特别注意法则 0：**这个阶段只定形状，不写契约**（字段级的东西，等某个模块真正接入时再定）。
> 现状：**准则是新的，代码是旧的**。旧代码与准则冲突的地方不是 bug，是待迁移清单（本文最后另列）。

---

## 准则 000（元准则）· 旧架构是「需求」，不是「骨架」

**准则**：
旧代码只用来回答"**有哪些功能不能丢**"，不用来决定"**新架构长什么样**"。
新架构由**契约**决定；内核与扩展两侧都按契约**重新生长**。

**为什么**（这条是本项目一条真实的分歧，记录完整推理）：
- 讨论中出现过一个诱人的建议：「现成的扩展宿主已经写了 287 行，契约直接长在它上面，别重复造。」
- 它错在把**代码复用**当成了**架构判断**：存在的东西不等于值得当基础。
- 更硬的理由是：那个宿主带着一个**错误的根假设**——它把记忆、桥接、身份对齐三个**完整服务对象**
  直接递给第三方扩展（`extensions.js:217-219`），等于假设"扩展是自己人"。
  以它为基础，就等于继承这个假设，而"扩展不是自己人"正是新架构要立的第一块砖。
- 还有一层：原仓库里有两套并行的接入机制（`extensions/` 与 `platforms/`，后者是空壳）。
  把契约挂到其中任何一套上，都会让"两套并存"更难拆。

**边界（最重要的一条，防止把"干净"执行成"失忆"）**：

> **"不用旧架构" ≠ "忘掉旧代码里的教训"。**

旧代码里有一批**用事故换来的规则**，必须被搬进新架构——但**搬的是"要求"，不是"代码"**：

| 旧代码里的教训 | 新家的形态 |
| --- | --- |
| 单实例锁里 EPERM 不能当"已有实例"（否则永久起不来） | 内核/管家的**规则**：未知 ≠ 为真 |
| 只读降级时接口曾回"已保存"，重启全丢 | 契约的**回执第五态**「已发出但无法确认」+ 失败必须可见 |
| 令牌可能被模型复述进消息 | 表达器（K6）的**出站检查**规则 |
| 沉睡观察必须真等够静默窗口 | 注意力漏斗（K3）的**硬约束**，不是提示词建议 |
| 记忆写入只能有一个写者 | 契约的 `remember` 只给**候选** |

**怎么执行（三步自检）**：
1. 设计某个部件时，问："这是**需求**（要保住什么），还是**实现**（旧代码怎么写的）？"——只后者的部分，不准带进来。
2. 每搬一个功能，先写"验收行为"，再写实现；**行为对不上旧系统就是没搬完**。
3. 每搬完一个能力，**立刻删掉旧路**（隔离到 `_quarantine` 也行）。**两条路并存 = 新的紊乱开始。**

**配套记录**：为什么这条是"元准则"——因为它管的是**其余所有准则怎么落地**。
其余准则是"设计成什么样"，这条是"从哪里出发"。

## 准则 001 · 能选的都让用户选，并且每个选项都要有默认值

**准则**：凡是有意义的选择，都给用户。不给"我替你挑好的唯一方案"。
但每个选项必须有**默认值**，不能给用户一堆空白让他自己填。

**为什么**：
- 强迫用户接受一个方案 = 替用户决定人生；用户会走。
- 但"什么都要用户选" = **选择过载**（选项一多，人反而不做决定），第一次打开就放弃。

**落地三件套**（每个选项都必须有）：
1. 一个默认值（推荐值）
2. 可选的其他档
3. 一句代价说明（更贵 / 更慢 / 更吵）

**边界**：**安全与正确性的底线不给开关**（见准则 002）。

## 准则 002 · 底线不给开关，其余都给

**准则**：凡是"关掉会导致事故"的选项，**不做成开关**，由系统强制。

**为什么**：自由不是无限的。给用户一把能拆掉刹车的钥匙，不叫尊重，叫事故入口。

**反例（绝不允许出现的开关）**：
- 「关掉发送白名单校验」
- 「关掉 token 出站检查」
- 「允许适配器直接读写记忆」
- 「关闭事件来源校验」

**边界**：判断方法是问一句——**"如果用户关掉它，出了事算谁的？"**
算用户的（如"我要不要被游戏战报打扰"）→ 给开关。
算"系统本来该保住的"（如"能不能伪造别人说话"）→ 不给。

## 准则 003 · 选项由适配器声明，界面由内核统一画，配置数据属于用户

**准则**：适配器只交一张"菜单纸"（有哪些选项、默认什么、可选什么、代价是什么）；
**界面由内核画，配置存在内核那边，并且能导出、能备份、能换机器带走。**

**为什么**（这条最硬的理由是安全）：
- 适配器是**第三方代码，一律不可信**。
- 如果适配器能自己造界面，它就能做出一个"请输入你的 QQ 密码"的框，
  而用户**分不清这是 SurfCore 的还是插件的**——这是钓鱼的温床。
- 另外：一千个适配器一千个界面，用户每装一个都要重新学一次。

**一句话**：**适配器是租户，不是房东。** 房子（界面、存储、用户）是内核的。

**边界**：适配器仍然可以有自己的"高级/危险"设置项，但必须走内核的菜单，并且要**标注风险**。

## 准则 004 · 谁更懂谁侦测；谁最关心谁有开关；谁有手谁执行

**准则**：三件事分给三个人，不许一个人全干。

| 事情 | 归谁 | 原因 |
| --- | --- | --- |
| **侦测**（什么时候算"发生了值得说的事"） | 懂那个世界的人（游戏扩展、平台适配器） | 它知道"3 点血"意味着什么 |
| **开关**（要不要被打扰、多久一次、多细） | 用户（通过适配器设置页） | 只有他知道自己想被怎么打扰 |
| **执行**（怎么发出去、发成什么样） | 适配器（有手的那一方） | 它知道那个平台的规矩 |

**为什么**：让扩展管偏好 = 它替用户决定；让用户管侦测 = 他得去懂游戏代码。两边都越界。

**边界**：一个适配器可以同时扮演"侦测者 + 执行者"（它本来就在那儿），
但**"开关"必须留在用户手里**。

## 准则 005 · 每个选项必须写代价；每加一个开关，记一笔测试账

**准则**：
1. 每个选项都要写清"选了会怎样"（更贵 / 更慢 / 更吵 / 更省）。
2. 每新增一个开关，都要在"测试账"上记一笔：**它会让多少种组合需要被验证。**

**为什么**：开关不是免费的。它一旦存在，就要一直存在、一直被测试、一直有人问"这个什么意思"。
组合还会相乘：3 档精细度 × 10 个渠道 = 30 种组合。

**边界**：允许多给开关，但要用**正交**的方式给（互不干扰），不要给"互相打架"的选项组合。

## 准则 006 · 谁更懂，谁过滤

**准则**：原始数据在"懂它的人"那里就压成结论，不要把原始数据丢给内核让它自己想。

**为什么**：内核读的每个字都花钱。把过滤甩给内核 = 让最贵的员工干最便宜的活。
（游戏每秒 20 次状态变化，内核只该看到"血 12/80，刚打完一群史莱姆"这一句。）

**边界**：过滤会丢信息。所以过滤后的东西必须**带来源**，并且允许用户把过滤调细（准则 001）。

---

## 准则 007 · 内核不联网、不认识渠道名、不直接读写别人的记忆

**准则**：三句话，一条都不能破。
1. **内核不联网**：所有跟外界的交互都经过适配器。
2. **内核不认识渠道名**：内核只读"能力"，不许出现"如果是 QQ 就……"。
3. **内核的记忆只有一个写者**：适配器只能"提交候选"，不能直接改。

**为什么**：
- 不联网 → 内核可以完全离线测试，也永远不会被诱导去访问坏网址（这类攻击叫 SSRF）。
- 不认识渠道名 → 加第 101 个渠道不用改内核。
- 单写者 → 记忆不会被第三方污染，可回溯、可审计。

**边界**：内核可以**读**环境信息（时间、磁盘空间）来判断成本与节奏，但不为适配器"代取"任何外部内容。

## 准则 008 · 内核不设"口味上限"，但必须守"承重上限"；裁剪必须可见

> 这一条是 2026-11-09 用户提出「内核不要定上限规则」后，讨论出来的精确版本。
> **结论：用户说对了一半。**

**准则**：
- **口味上限**（"你最多看 6 帧图"）→ **内核不设**。这是用户的偏好，归准则 001。
- **承重上限**（"一次事件超过 X 兆直接拒收并报错"）→ **内核必须有**。这是防崩溃，不是偏好。

**为什么**（比喻）：
装修随你改，承重墙不能拆——不是不尊重你，是因为拆了整栋楼塌。
一个写得烂的适配器（或恶意适配器）如果一次塞 500 兆进来，内核会直接死掉；
死了之后**用户的"选择"全部失效**，比不给选择更糟。

**所以内核只做两件事，都不侵犯用户自由**：
1. **装不下时按用户选的优先顺序裁剪**（省钱优先 / 细节优先 / 均衡），
   并且——**必须告诉用户"我裁了"**。
2. **把代价算给用户看**（按你现在的设置，这个月大概要花多少），
   让用户**在付钱之前**改主意。

**最关键的半句**：**裁剪必须可见。**
悄悄地少看几帧、悄悄地截断，等于"假成功"——用户以为自己的选择生效了，其实没有。
（这个系统历史上已经出过一次同类事故：存储写不进时接口仍回"已保存"，重启后全丢。）

**边界**：承重上限的具体数值由**实现**决定并随硬件/模型变化，但**必须在文档里写清、在报错里说明**。

## 准则 009 · 事件必须有信封；不认识的事件必须忽略

**准则**：
1. 任何上报的事件，必须带**信封**：谁发的、哪个渠道、什么时候、编号、类型。
2. **来源由内核盖章**，不许适配器自称（否则 A 可以假冒 B 说话）。
3. 内核遇到**不认识的事件类型，必须安静忽略**，不许崩溃、不许报错刷屏。

**为什么**：
- 信封是"可追溯"的前提。没有信封的事件，出了问题查不清。
- 第 3 条是**前向兼容**的唯一办法：今天接 5 个渠道，明天有人加了新事件类型，
  不该让整个系统炸掉。

**边界**：忽略不等于不记——不认识的事件要记一行审计，方便日后诊断。

---

## 准则 010 · 适配器一律不可信：默认拒绝、最小权限、可审计、卸载不留孤儿

**准则**：
1. **默认拒绝**：没声明能做，就是不能做。
2. **最小权限**：只拿它声明过、且用户同意过的能力。
3. **可审计**：它报了什么、发了什么、读了什么（唯一能读的那一窄口），都要留痕。
4. **卸载不留孤儿**：删除适配器时，它的配置、状态、订阅要能被完整清掉。

**为什么**：一旦允许第三方接入，"信任"就必须从"相信人"变成"设计上不可能作恶"。

**边界**：内置适配器（QQ/B站/桌宠）也建议走同一套规则——**例外就是漏洞的开始**。

## 准则 012 · 依照能力清单管理

**准则**：
凡是"能不能做某件事"，**只由能力清单回答**。
适配器声明、用户授权、内核放行、界面展示、测试覆盖、审计留痕——**全部以清单为唯一依据**；
清单外的能力，一律不产生任何权限。

**为什么**（三条实测缺陷，正是需要它的理由）：
1. 扩展的 `capabilities` 是**自由字符串数组**，只 `map(String).slice(0,20)`（`extensions.js:38`）——谁都能写任何词；
2. 这份声明**从不参与任何行为判断**——说"我能改配置"，内核也不会因此多给或少给权限，声明成了装饰品；
3. 同一个仓库里 `platforms.js:40-42` 反而按 `PLATFORM_CAPABILITIES` 过滤——**两套规矩**。

只要"权限"靠每个 API 自己记得检查，**就一定会漏**（这与准则 007「判据只能有一份实现」是同一个道理）。

**边界（四条，缺一条就会退化成"装饰性能力"）**：

1. **能力 ≠ 禁止项。** 能被授权给第三方的叫**能力**；只有"允许/不允许"、永远不许授权的叫**禁止项**
   （伪造来源、绕过白名单、直写记忆、自己画界面）。把禁止项写成能力 = 给了一把拆刹车的钥匙。
2. **未知能力：回告"不支持"，不静默忽略、也不拒绝注册。**
   静默忽略 → 适配器以为能用，跑起来才炸；直接拒绝 → 新能力永远上不了旧内核。
3. **高危默认关、单独授权、可随时撤销、每次使用都记审计**；撤销后立即生效，不留残余。
4. **清单即测试矩阵**：每个能力 2 条用例（声明了能用 / 没声明能优雅降级），高危能力再加 1 条
   （关掉时必须**拒绝**而不是降级）。

**落地**：[能力清单与清单式治理](CAPABILITY-REGISTRY.md)（两类能力 + 禁止清单 + 校验/授权/运行期规则 + 差距与迁移）。

## 准则 013 · 可添加性：形状固定，条目开放

**准则**：
契约只规定**"一条能力 / 一个事件怎么写"**（形状），**不规定"有哪些"**（条目）。
新增一个渠道、一种能力、一类事件，**不应该需要修改契约本身**。

**为什么**（这条来自一次真实的设计错误）：
- 初稿把能力列成封闭清单（15 项物理 + 11 项授权），并要求"必须命中清单"。
- 后果是：**每加一个新渠道就得改契约**——这不叫抽象接口，这叫"提前把未来钉死"。
- 而且它隐含一个不可能的前提：*"我现在就知道你以后要接什么。"*

**分界原则（这条是核心）**：

> **闭的是"内核的语言"，开的是"外部的声音"。**

| | 开放/封闭 | 判据 |
| --- | --- | --- |
| 渠道能力 | **开** | 外部自述"我能干什么"。内核认识就据此改变行为，不认识就记录+忽略 |
| 事件 | **开** | 外部上报"发生了什么"。不认识的忽略并记审计 |
| 意图 | **闭** | 这是内核"要说的话"，它只会说会的几句；渠道特有动作交给 `act` |
| 权限（授权能力） | **闭** | 内核不理解一个权限就无法约束它 → **不认识就不给** |
| 形状（编号格式） | **固定** | 不认识的东西也要有规矩，才能被安全忽略 |

**边界（三条，防止把"开放"执行成"没有规矩"）**：
1. **开放 ≠ 无格式**：编号必须合规则（2~3 段小写点号），否则连"忽略"都不安全。
2. **开放 ≠ 无准入**：形状错、协议版本不符、出现禁止项，仍然**拒绝注册**。
3. **开放只针对"外部自述"**；凡是**内核要据此做安全决定**的（权限），必须封闭。

**落地**：[适配器契约 v2](../../contracts/adapter-contract.js) 的校验函数已实现这个不对称——
未知渠道能力/事件→放行并记"未识别"；未知授权能力→不授予；未知意图→警告。

把上面十条压成一张清单，作为接口设计的验收表：

| # | 接口必须提供 | 来自哪条准则 |
