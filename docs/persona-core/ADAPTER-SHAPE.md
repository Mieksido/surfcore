# 适配器形状（不含字段）

> 这份只回答三件事：**有哪几块、谁跟谁说话、信息怎么流。**
> **不写字段名、不写格式、不写错误码**——那些属于"某个模块真正接入时"才定的契约
> （见 [架构法则](ARCHITECTURE-LAWS.md) 法则 0 与法则 10）。
>
> 立文：2026-11-09。基线高度由用户确认：**平台来源 / 平台 ID / 信息（文本、图像、音频）**。
> 本文所有"我加的"内容都在 §9 单独标出，方便删。

---

## 0. 一句话

> **一个渠道 = 一个适配器。适配器只做三件事：把外面的事报上来、把她的话办下去、把办的结果报回去。**

---

## 1. 全景

```text
      外部世界                 适配器（每个渠道一个）                    人格内核
  ┌────────────┐   ┌──────────────────────────────────────┐   ┌────────────────┐
  │ QQ 群/私聊  │   │ ① 身份   平台来源 + 平台实例 + 账号 + 频道 │   │  她（人格）      │
  │ B站 动态    │◄─►│ ② 能力   收发形态 / 时序 / 频率 / 特殊    │◄─►│                │
  │ 某游戏      │   │ ③ 菜单   可调项（声明在这、界面在内核）    │   │  身份 / 记忆    │
  │ 只读屏      │   │ ④ 生命   上班 / 报平安 / 下班 / 卸载清场   │   │  时机 / 预算    │
  └────────────┘   └──────────────────────────────────────┘   └────────────────┘
                         上行：事件 · 内容 · 回执
                         下行：意图
```

**方向是单向的**：适配器认识内核（照它的规矩说话），内核**不认识**任何适配器（不知道 QQ 是什么）。
这就是"加第 101 个渠道不用改她"的全部机制。

---

## 2. 第一块：身份（两半，不是一件事）

身份其实是**两件不同的事**，内核用它们做**不同的判断**——所以必须分开记：

### 2.1 谁做的（这份软件的身份）

| 概念 | 回答什么 | 内核拿它干什么 |
| --- | --- | --- |
| **发布人** | 这份软件是谁做的 | 判断**信任**：官方？社区？你自己写的？ |
| **适配器名字** | 它叫什么 | 同一个发布人下不重复 |
| **版本** | 第几次发布 | 判断**兼容**：跟我的规矩对不对得上 |

**展示时合成一个**：`发布人@版本`，例如 `surfcore@1.4.0`。

> **为什么不是"一个字符串版本号"**：因为内核要拿它们做两件不同的事。
> 合成成一个字段，将来想单独判断"这是谁做的"就得拆字符串——**拆字符串是脆弱的**。
>
> **重要后果**：**同一个名字、不同发布人 = 两个不同的适配器**，不能混用（信任等级不同）。
> 没有发布人，用户根本分不清自己在开谁的软件。

### 2.2 在跟哪个世界说话（渠道坐标，四层）

一个"平台来源"是不够的——QQ 里有群、有私聊、有多个账号。所以坐标是**四层**：

| 层 | 回答什么 | 举例 |
| --- | --- | --- |
| **平台来源** | 这是哪种世界 | QQ / B站 / 某游戏 / 一个只读屏 |
| **平台实例** | 这个世界里的哪一份 | 某个服务器、某个机器人账号 |
| **账号** | 用谁的身份在说话 | 她自己的那个号 |
| **频道** | 具体在哪个房间/对话框/世界 | 某个群、某个私聊、某个存档 |

> **为什么必须分层**：如果只有"平台来源 + ID"，那么"同一个群里两个人"和"两个群里同一个人"就没法区分，
> 而她**需要知道"我在跟谁说话"**——这是同一件事在不同层的两半。

---

## 3. 第二块：能力（用"维度"而不是"清单"）

**这是"通用性"的真正来源。** 不列"我能干什么"的清单，而是给每个渠道**在几条轴上定位**。

| 轴 | 一端 | 另一端 | 谁落在两端 |
| --- | --- | --- | --- |
| **时序** | 实时（秒级） | 异步（按天算） | 游戏回合 ↔ 邮件、留言板 |
| **形态** | 一条一条 | 连续流 | 群消息 ↔ 电话、直播 |
| **身份** | 一定有身份 | 可能匿名 | QQ ↔ 传真、匿名投稿 |
| **方向** | 双向 | 单向 | 聊天 ↔ 广播、公告屏 |
| **频率** | 低频 | 高频 | 聊天 ↔ 游戏每秒多次 |
| **模态** | 纯文本 | 多模态 | 终端 ↔ QQ、抖音 |

**用法**：接到一个新平台，不写"如果是直播就……"，而是**在六条轴上标个点**。
内核读这六条轴，就知道该怎么对她（能不能抢话、要不要等她、能不能发图、多久催一次）。

> 这就是"业务不认识外部世界，只认识接口"（法则 11）的落地：
> 内核不认识"直播"，只认识"**流式 + 实时 + 单向？**"。

**另外三类"特殊行为"不是轴，是开关**（有就有，没有就没有）：
能不能撤回、能不能编辑、有没有已读回执。

---

## 4. 第三块：菜单（可调的东西）

**三句话讲完：**
1. **谁声明**：适配器交一张单子——它有哪些可调项、默认是什么、还有哪些档、选贵的会怎样。
2. **谁画界面**：**内核统一画**。适配器不许自己画（否则能伪造登录框骗密码）。
3. **谁存**：**内核存**，所以能导出、能备份、能换机器带走。

> 这是"用户的眼睛归谁管"：适配器是**租户**，不是房东。

---

## 5. 第四块：生命（活着与退出）

| 阶段 | 要做什么 |
| --- | --- |
| **上班** | 连上那个世界，开始盯着 |
| **报平安** | 定期说"我还活着"；内核收不到就判定它死了 |
| **下班** | 优雅停：停之后不许再往上报任何东西 |
| **卸载** | 清掉自己留下的一切（配置、订阅、状态），**不许留孤儿** |

> **为什么"报平安"必须是形状的一部分**：适配器悄悄死掉时，内核会**对着空气说话**，而没人发现。

---

## 6. 上行：一条信息长什么样

### 6.1 三个必答

任何一次上报，必须能回答：**谁说的 / 在哪个频道 / 发生了什么。**
（"谁"在匿名渠道上可以没有——这一点必须**允许缺**，否则匿名渠道第一天就崩。）

### 6.2 内容：四类

这是你确认的高度，前三类是你定的，第四类是我加的（见 §9）：

| 类别 | 装什么 | 例子 |
| --- | --- | --- |
| **文本** | 文字本身 | "在吗"、"血 12/80" |
| **图像** | **路径 + 文字说明** | 一张猫图 → 存下来，附一句"群里有人发了只猫" |
| **音频** | **路径 + 文字说明** | 一段语音 → 存下来，附转写出来的那句话 |
| **结构化状态**（我加） | 世界/局面的**当前样子** | 血量、坐标、手牌、背包 |

### 6.3 核心规矩：传"替身 + 路径"，不传原件

你说的"路径 + 文字说明"，正好是这条规矩的形状：

- **给她的**：是"能读懂的那一小份"（说明文字、缩略图、转写稿、几张关键画面）；
- **留在路径上的**：是原件。她需要细看时，按路径去取。

**为什么**：原件又大又贵（模型按量收费），而且原件里什么都有（别人的脸、房间、聊天记录）。
**给她"能读懂的一小份"，是省钱、也是隐私。**

> ⚠️ 一个必须记住的坑：**路径会过期**。很多平台的图片链接有时效、要登录态才能取。
> 所以"路径"只能当**标识**，不能承诺"以后还能取"——**要存就当场存好**。

### 6.4 时序（三件必须说清的事）

| 事 | 为什么要说清 |
| --- | --- |
| **什么时候发生的** | 记忆排序、判断"刚才"还是"昨天" |
| **是不是同一条**（去重） | 同一条消息被重复推送，不能让她回两遍 |
| **在回哪一条**（引用关系） | "他这句话是在回谁"——这是聊天能不能听懂的前提 |

---

## 7. 下行：她能让它做什么

不列字段，只列**动作类别**：

| 动作 | 意思 |
| --- | --- |
| **说** | 说一句话 |
| **发内容** | 发图 / 语音 / 视频 / 表情 |
| **做** | 执行一个动作（游戏/世界里的指令；**具体动作名由渠道自己定，内核不枚举**） |
| **问** | 提一个问题，等人回答 |
| **沉默** | **显式地决定不说**（这是一个决定，不是"什么都没发"） |
| **收尾** | 记下"这次聊到哪、下次怎么接" |
| **记住** | 提交一条**记忆候选**（内核决定收不收） |
| **取消** | 打断正在进行中的输出（电话里她能停口） |

两条要点：
- **"沉默"必须是动作**，否则你永远查不到"她为什么没回我"。
- **"记住"只是候选**：写记忆的只有内核一个人（单写者，法则 14）。

---

## 8. 往返：办到没有（五类结果）

| 结果 | 意思 | 内核该怎么办 |
| --- | --- | --- |
| 办到了 | 发出去了 | 记账 |
| 失败了 | 出错 | 重试或告诉她 |
| 做不到 | 这渠道没这能力 | 换个表达方式 |
| 被限流 | 太频繁 | 排队等 |
| **已发出，无法确认**（我加） | 像传真：交出去了，但不知道对方收没收到 | **既不算成功也不算失败**，如实在界面说明 |

> 第五类是我加的：短信、邮件、广播、传真都属于这一类。**少这一类，系统就会撒谎。**

## 9. 我大胆补的（标记出来，方便你删）

| # | 我加的 | 为什么加 | 删掉会怎样 |
| --- | --- | --- | --- |
| 1 | **结构化状态**（第四类内容） | 游戏/世界的状态既不是文字也不是图片，是数据；塞进"文本"会让内核以为那是一句话 | 我的世界、杀戮尖塔这类**做不了**（只能靠人话摘要，丢精度） |
| 2 | **六条能力轴** | 通用性靠"定位"而不是"枚举渠道类型"；否则每接一个平台就要内核加特判 | 只能列渠道类型清单 → 又回到"每加一个平台改一次内核" |
| 3 | **身份四层**（来源/实例/账号/频道） | 只写"平台 + ID"分不清"同群两人"和"两群一人" | 群里多人对话会串，她分不清谁是谁 |
| 4 | **回执第五类**"已发出无法确认" | 大量真实渠道没有回执 | 系统会**把"不知道"说成"成功"** |
| 5 | **生命的四段**（含报平安） | 适配器悄悄死掉时没人知道 | 她对着空气说话，故障静默 |
| 6 | **时序三件事**（时间/去重/引用） | 没有它们，她会重复回复、听不懂"他在回谁" | 群聊基本不可用 |
| 7 | **"沉默"作为动作** | 沉默是决定，需要可查 | 永远查不到"她为什么没回" |
| 8 | **"记住"只是候选** | 保记忆单写者 | 多平台并发写记忆 → 互相覆盖 |

**每一条都能删**——但删掉要在文档里记一句"我们决定接受这个后果"。

## 10. 这份形状**不**决定什么（留给接入时）

明确划界，免得又被提前定死：

| 不决定 | 什么时候定 |
| --- | --- |
| 每个概念的**字段名** | 第一个真实适配器接入时 |
| 内容的**编码格式** | 同上 |
| 具体**错误码** | 同上 |
| **能力轴上怎么打分**（连续值还是档位） | 同上 |
| 菜单项的**控件类型**（开关/单选/滑块） | 界面实现时 |
| 版本号机制的具体形状 | 真有第二个版本要兼容时 |

## 11. 谁跟谁说话（关系图）

```text
   适配器 ──上报事件/内容/回执──► 内核
   适配器 ◄──下发意图──────────  内核
   适配器 ──读"她是谁"（仅公开档）─► 内核

   内核 ──不认识任何适配器───────  ✗
   适配器 ──不认识记忆/文件/网络──  ✗
```

**两条"✗"是这份形状里最重要的两笔。**

---

## 12. 通用性自检：任何新平台，先问这六个问题

接到一个新渠道，不用画新图，只填这六格：

1. **时序**：实时还是异步？
2. **形态**：一条一条，还是连续流？
3. **身份**：一定有身份，还是可能匿名？
4. **方向**：双向，还是只能往外推？
5. **频率**：人说话的速度，还是每秒很多次？
6. **模态**：只有文字，还是能发图/语音/视频？

**六格填完，内核就知道怎么对她了——不需要为这个平台改内核。**
这就是"通用"的判据：**新平台只填六格，不改代码。**

## 13. 下一步（等你点头）

按 [架构法则](ARCHITECTURE-LAWS.md) 法则 12，下一步是**假适配器**：
用这份形状写一个**终端适配器**（只有"平台来源、频道、文本"三样，其它都空着），
再写一个最小内核，验证"**她能收到、能回、能选择不说**"。

验收标准只有一条：**为了让它跑起来，内核不需要改一行。**
