## 1. 目标状态（怎么算"搬完了"）

不是"新代码能跑"，而是下面五条**同时成立**：

| # | 判据 | 怎么验 |
| --- | --- | --- |
| 1 | **内核里没有任何渠道名** | 在内核代码里搜 `qq` / `bili` / `pet`，结果为 0 |
| 2 | **每个渠道是一个独立目录** | `adapters/<渠道>/` 各自带身份、能力、菜单、生命、三管 |
| 3 | **不启动整个世界也能验** | 只跑内核 + 终端假适配器，就能验"收、想、说、沉默、记住" |
| 4 | **旧单体退役** | `src/bridge.js`（17,801 行）被替代或隔离到 `_quarantine/`，不再是运行路径 |
| 5 | **行为对拍一致** | 同一个功能：新旧各跑一遍，结果一样（不是"看起来差不多"） |

**外加一条适应度函数**（法则 16）：把第 1 条做成**会自动变红的检查**，进日常门禁。
否则半年后又会长出新的 `if (渠道 === 'qq')`。

## 2. 迁移顺序（有依赖关系，不是随便排的）

```text
第 1 步  终端假适配器 + 最小内核闭环      ← 验证"形状对不对"，不含任何旧功能
第 2 步  基础设施（配置/路径/护栏/环境）  ← 新内核也得读写配置，但这层没有业务
第 3 步  记忆（含媒体库）                 ← 三渠道共用、最烂（30+ 平台判断）
第 4 步  身份与人格                       ← 她是谁（记忆之外的另一个地基）
第 5 步  时机（唤醒/收尾/目的/问候）      ← 什么时候开口
第 6 步  预算（额度/账本/计价）           ← 能花多少
第 7 步  内容处理（文本/表情/黑话/转发）  ← 她说话的手艺
第 8 步  QQ 渠道                          ← 最大最难，第 3~7 步是它的前置
第 9 步  语音能力                         ← 能力与渠道分离的试验田
第 10 步 桌宠渠道                         ← 比 QQ 简单，复用第 8 步的经验
第 11 步 B站 渠道（含工具链、生物钟）     ← 独立子系统，很多东西天生属于"渠道业务"
第 12 步 运维（更新/体检/备份/兼容）      ← 最后搬，因为它服务于"搬完后的系统"
```

### 为什么是这个顺序（四条依据）

1. **先假后真**：没有假适配器，就无法判断"是内核错了还是渠道错了"（法则 12）。
2. **先共用后专用**：记忆/身份/时机/预算被三个渠道共用，先搬它，后面每搬一个渠道都在复用它。
3. **先易后难但瓶颈前置**：QQ 最难的依赖（记忆、时机）必须先在，所以 QQ 排第 8 而不是第 2。
4. **B站 最后**：它体量最大（调度器 1,374 行 + 34 个 CLI 命令 + 生物钟），而且它大量逻辑**本来就该在渠道里**，
   放在最后可以积累最多经验，减少返工。

## 4. 每个单元怎么搬（固定五步，不许省）

```text
① 写"行为清单"   ← 旧系统在这个功能上，具体会做什么（可观察的）
② 写验收          ← 清单里每条对应一个能被自动验的断言
③ 在新架构实现    ← 内核侧 or 适配器侧（按法则 2 放对位置）
④ 对拍            ← 同一批输入，新旧结果比对
⑤ 删旧路          ← 隔离旧实现，删掉调用点
```

**为什么第 ① 步最重要**：模块清单能保证"不漏模块"，但保证不了**"不漏行为"**。
旧代码里有一批用事故换来的细节——比如"沉睡观察必须真等够静默窗口"、"只读降级必须返回失败而不是假装成功"、
"单实例锁里 EPERM 不能当成已有实例"。**这些不在模块名里，只在行为里。**

> 判据：如果一条行为你写不出来，说明你还没读懂那块旧代码——**先读懂，别搬**。

## 5. 风险与对策（提前写，免得事后找理由）

| 风险 | 会发生什么 | 对策 |
| --- | --- | --- |
| **行为细节丢失** | 新系统功能都在，但她"变了一个人"（该沉默时说话、该等时不等） | §4 第①步的行为清单 + 第④步对拍；每条行为都要有断言 |
| **两套并存变永久** | 旧 `bridge.js` 永远删不掉，最后谁也不懂全貌 | §4 第⑤步硬性执行；旧实现只许 rename 到隔离区，不许"先留着" |
| **形状被现实打脸** | 搬 QQ 时发现能力轴不够、事件类别缺东西 | 这是**预期之内**（工作方式 1）。改形状 → 记原因 → 回改已迁移的适配器；**不许为某个渠道打补丁** |
| **规模太大做不完** | 17,801 行不可能一次搬完 | 按单元、按子单元小步；每个单元都能独立验收、独立停 |
| **并行开发互相踩** | 新旧同时改，冲突不断 | 一会话一工作树（AGENTS §1.9）；旧系统在这期间**只修 P0**，不加新功能 |

## 7. 下一步：第 1 步的具体定义

**目标**：证明"内核不认识渠道"这件事是真的。

| 做 | 不做 |
| --- | --- |
| 终端适配器（身份 `surfcore@terminal@0.1.0`，只填来源/频道/文本三格） | 不接 QQ、不连网 |
| 最小内核：收事件 → 判断要不要回 → 说 / 沉默 | 不做记忆持久化、不做预算 |
| 一条自动检查：内核代码里 grep 不到渠道名 | 不做界面 |

**验收三条**：
1. 终端里能跟她对话；
2. 她能**选择不说**（沉默是一个决定，可观察）；
3. **为了它跑起来，内核没有改过一行**（改了，说明形状不对）。
