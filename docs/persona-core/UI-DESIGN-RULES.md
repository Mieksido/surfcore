# SurfCore UI 设计准则

> 这份文件是**设计 UI / 写前端之前必须先对一遍的准则**。
> 适用：SurfCore 的壳（`D:\deepseekwork\surfcore-ui`）以及未来任何控制台/桌宠/管理端。
> 核心一句话：**UI 是壳，不是后端的镜像；用户看到的是任务，不是接口目录。**

---

## 0. 五条总原则

1. **先读后端，再画页面。**
   先建立后端地图：有哪些模块、真实接口、状态、错误、数据形状；再决定 UI。
   不能因为后端有一个接口，就认为前端必须有一个按钮。

2. **按用户任务划分，不按后端文件夹划分。**
   页面回答“用户要完成什么”，不是“后端有哪些模块”。
   高频功能放容易到达的位置；低频高级功能放二级页面；相关功能聚合；不制造只为展示功能的空页面。

3. **前端不能创造业务状态。**
   前端可以有交互状态（弹窗开着、tab 选中、输入草稿、按钮禁用），
   但“是否启动/是否在线/是否送达/任务进度”必须以**后端契约**为准。
   不能点击后直接把“启动”改成“已启动”。

4. **每个功能必须有完整状态。**
   至少考虑：未连接 / 正在连接 / 已连接 / 连接失败 / 正在断开 / 状态未知。
   未知就是未知，不伪装成离线，也不伪装成在线。

5. **视觉统一，工程可维护。**
   科幻风格贯穿所有页面；颜色、字体、间距、圆角、阴影、图标、动效、组件库统一。
   页面 / 组件 / Hooks / API / 类型 / Store 分层，不写成一个巨大组件。

## 1. 设计工作流（顺序不要反）

### 第 1 步：后端地图

先列出并读懂：

- 模块与职责（哪些是内核、哪些是包、哪些是壳）；
- 真实接口/方法：输入、输出、错误码、幂等性、权限；
- 哪些是**用户功能**，哪些是**内部服务/调试数据**；
- 哪些数据是实时、哪些是快照、哪些是历史；
- 哪些能力还没有接口（标记「待补充」，不编造）。

产出：**后端能力表**（模块 / 接口 / 数据 / 状态 / 缺口）。

### 第 2 步：功能模块与用户任务

先分模块，再分页面。按用户任务划分：

- 用户是谁？要完成什么任务？
- 任务的完整路径是什么（进入 → 操作 → 等待 → 成功/失败 → 返回/重试）？
- 哪些是高频？哪些是一次性/高级？哪些只是调试？
- 哪些功能应该合并成一个操作流程，而不是拆成多个按钮？

产出：**功能地图 + 任务流**。

### 第 3 步：页面清单

页面划分规则：

- 按用户任务，不按后端目录；
- 高频入口放在一级；
- 低频高级功能放二级/折叠；
- 相关功能尽量聚合；
- 页面不要切得过碎；
- 不为“展示功能”制造没有实际价值的页面；
- 调试数据不单独做用户页面（除非明确是开发者工具）。

产出：**页面清单 + 每页目标 + 入口/返回路径**。

### 第 4 步：接口映射表（必须）

每个用户交互都要有明确的后端依据：

| 用户动作 | 页面 | 后端接口/方法 | 数据来源 | 状态 | 缺失/备注 |
| --- | --- | --- | --- | --- | --- |
| 看当前状态 |  |  |  |  |  |
| 启动/停止 |  |  |  |  |  |
| 保存设置 |  |  |  |  |  |
| 搜索/分页 |  |  |  |  |  |
| 重试/刷新 |  |  |  |  |  |

规则：

- 没有接口 → 写 **「待补充」**，不要编造；
- 不把内部接口包装成用户按钮；
- 不把调试数据当业务数据；
- 不擅自修改后端业务逻辑；
- 严格遵循 API 契约（字段名、错误码、分页方式）。

### 第 5 步：组件与异步状态

确定页面后，再设计组件。每个组件必须想清楚：

- 加载中什么样？
- 没有数据什么样？
- 请求失败什么样（原因 + 重试）？
- 数据过多怎么分页/滚动？
- 用户改时间范围/筛选后怎么刷新？
- 切走页面再回来，数据保留还是重取？
- 请求还没回来，用户又点了一次怎么办？
- 页面卸载后，请求/订阅是否停止？
- 旧请求的结果会不会覆盖新状态？

### 第 6 步：视觉

最后才决定长什么样。**不要每做一个页面就重新发明一套规范。**

## 2. 状态模型（不能只有“连接/断开”）

| 状态 | UI 表现 |
| --- | --- |
| 未连接 | 显示连接/启动按钮 |
| 正在连接 | Loading；按钮禁用，禁止重复点击 |
| 已连接 | 显示在线/健康状态 |
| 连接失败 | 显示原因 + 重试按钮 |
| 正在断开 | 显示断开进度；按钮禁用 |
| 状态未知 | 显示“未知/无法确认”；不伪装成离线 |

适用于所有异步动作（启动、停止、保存、发送、导入、重建索引）。

### 动作状态机

```text
idle → submitting → success
             └──→ failed → retry
             └──→ unknown（超时/断线：不能当成功，也不能当失败）
```

**启动桌宠的例子：**

```text
点击“启动”
  → 前端进入 submitting（按钮显示“启动中”，禁用）
  → 等后端确认进程真的启动
  → 成功：显示“运行中”
  → 失败：显示错误原因 + 重试
  → 超时/无法确认：显示“状态未知”，不显示“已启动”
```

前端不能点完就把按钮改成“停止”。

## 3. 前端状态 vs 后端状态

| 前端状态（UI 可以自己管） | 后端状态（必须由契约确认） |
| --- | --- |
| 弹窗是否打开 | 进程是否真的启动 |
| 当前 tab | 服务是否真正健康 |
| 输入框草稿 | 消息是否成功送达 |
| 按钮是否禁用 | 任务真实进度 |
| 表格排序/筛选 | 数据是否真的保存 |
| 请求进行中 | 是否真的断开 |

前端状态用于交互，**不能当成业务事实**。

## 4. 数据获取与实时更新（统一机制）

先回答这些问题，再写代码：

- 哪些数据通过 **HTTP 请求**获取？
- 哪些通过 **WebSocket/SSE 推送**？
- 哪些需要**定时轮询**？
- 哪些只在**用户手动刷新**时获取？
- 断线后如何恢复？
- 页面关闭后是否停止订阅/轮询？
- 是否可能收到重复事件？
- 旧请求的结果是否可能覆盖新状态？

硬规则：

1. **不要给每个页面随意加 `setInterval`。**
   用统一的数据更新层/调度器。
2. 轮询只在页面可见时进行；页面隐藏/卸载要停。
3. 断线恢复：先重连，再拉一次快照，避免只靠增量。
4. 推送事件要有唯一 id；重复事件要幂等。
5. 请求要有 generation/requestId；旧响应不能覆盖新状态。
6. 超时/断线是「未知」，不是成功，也不是失败。
7. 实时数据要标明来源（快照/推送/轮询/手动），避免用户误以为都是实时。

## 5. 页面 / 组件 / 工程分层

- **页面**：只负责布局与组合。
- **组件**：可复用 UI（按钮、输入、表格、卡片、弹窗、空态、加载、错误）。
- **Hooks / Composables**：交互状态与数据逻辑。
- **API 层**：接口请求、错误归一、取消、超时。
- **类型定义**：约束后端数据结构。
- **Store**：跨页面共享状态（只放真正共享的）。
- **不写巨大组件**；不把请求逻辑散落在每个组件里。

UI 不是后端镜像：后端可以复杂，用户不应该被迫理解后端复杂度。

## 6. 视觉规范（科幻风格，统一）

当前壳是深蓝/青色科幻风。**禁止点开一个页面变成纯白或纯黑整个背景。**

### 6.1 颜色 token

| 用途 | 值 |
| --- | --- |
| 页面背景 | 深蓝黑渐变 `#03060d` / `#06101f` |
| 面板背景 | 半透明深蓝 `rgba(8,20,38,.85)` |
| 主色/强调 | 青色 `#22d3ee` / 亮蓝 `#7dd3fc` |
| 主文字 | `#cfe6ff` / `#eaf9ff` |
| 次要文字 | `#5f8fbb` / `#8fb6da` |
| 成功 | `#22c55e` |
| 警告 | `#eab308` |
| 错误 | `#f87171` / `#fca5a5` |
| 边框/分隔 | 青色低透明度 `rgba(125,211,252,.18~.45)` |

### 6.2 字体

- 中文/UI：`"Segoe UI", "Microsoft YaHei", sans-serif`
- 数字/代码/版本：等宽 `ui-monospace, "Cascadia Code", monospace`
- 字号层级：10 / 11 / 12 / 13 / 16 / 22 / 28
- 字重：400 正文，600 小标题，700 强调，900 大标题
- 数字使用 tabular-nums

### 6.3 间距

4 / 8 / 12 / 16 / 24 / 32；页面边距 20–28；卡片内边距 10–18；组件间距 8–16。

### 6.4 圆角

按钮 8；输入 8；卡片 12–16；弹窗 16；胶囊 999。

### 6.5 阴影/层级

- 面板：内描边 + 轻微内发光；
- 悬浮：外层青色 glow；
- 弹窗：最高层，背后遮罩；
- 不靠巨大的纯黑阴影做层级。

### 6.6 图标

统一线性图标；16/20px；同一套图标库；不要混用实心/彩色/emoji 风格。

### 6.7 动效

- 悬浮 160ms；
- 展开/切换 220–300ms；
- 页面进出 400–600ms；
- Loading 用统一骨架/旋转，不用随机动画；
- 尊重 `prefers-reduced-motion`。

### 6.8 组件库

按钮、输入、选择、开关、表格、卡片、Tabs、弹窗、Toast、空态、加载骨架、错误块、分页。
**同一组件只实现一次**，所有页面复用。

## 7. 开发规范（12 条）

| # | 规则 | 为什么 |
| --- | --- | --- |
| 1 | 不擅自修改后端业务逻辑 | 防止前后端职责混乱 |
| 2 | 严格遵循 API 契约 | 防止调用错误 |
| 3 | 不虚构数据 | 防止假数据冒充真实 |
| 4 | 统一状态管理 | 防止同一状态不同页面不一致 |
| 5 | 完整处理异步状态 | 加载/失败/成功/未知不能缺 |
| 6 | 防止重复提交 | 避免重复启动/发送 |
| 7 | 处理组件生命周期 | 退出后停止请求/订阅 |
| 8 | 处理实时数据更新 | 避免状态长期不刷新 |
| 9 | 统一错误处理 | 不每页自己随意处理异常 |
| 10 | 保证组件可复用 | 避免重复开发 |
| 11 | 考虑窗口尺寸变化 | 避免缩放后布局崩溃 |
| 12 | 保留可观测性 | 方便定位接口/渲染/交互问题 |

补充：

- 错误必须可见、可行动：`code / message / hint / retryable`；没有契约就标「待补充」。
- 加载、空、错误、超时、无权限都要有 UI。
- 关键操作要确认（重建索引、清空、停止服务）。
- 不在 UI 里拼后端业务规则。

## 8. 交付物（每次设计 UI 先输出这些）

1. **后端地图**：模块 / 接口 / 数据 / 状态 / 缺口。
2. **功能地图**：用户任务、完整路径、高频/低频、内部/调试。
3. **页面清单**：目标、入口、返回、聚合关系。
4. **接口映射表**：每个交互 → 后端依据；缺失写「待补充」。
5. **状态矩阵**：每个组件/动作的 loading/empty/error/success/unknown/disabled。
6. **数据更新策略**：HTTP / WS / 轮询 / 手动；断线恢复；去重；旧请求覆盖。
7. **视觉 tokens**：颜色/字体/间距/圆角/阴影/图标/动效/组件。
8. **工程分层**：页面/组件/Hooks/API/类型/Store。
9. **风险与待补充**：没有接口的功能、调试数据、未来扩展点。

## 9. 浓缩提示词（以后每次设计 UI 发这段）

```text
你是 SurfCore 的 UI 设计/实现 agent。先读后端，再画界面；UI 是壳，不是后端镜像。

一、先建后端地图
- 列出模块、真实接口/方法、输入输出、错误码、权限、数据形状。
- 区分用户功能 / 内部服务 / 调试数据；没接口就标「待补充」，禁止编造。
- 不因后端有接口就给前端加按钮；不擅自改后端业务逻辑。

二、按用户任务设计
- 先分功能模块，再分页面；按用户任务，不按后端文件夹。
- 高频入口一级；低频高级功能二级；相关功能聚合；不制造展示型空页面。
- 画出用户完成任务的全路径：进入→操作→等待→成功/失败→返回/重试。

三、状态必须完整
- 连接类至少：未连接/正在连接/已连接/连接失败/正在断开/状态未知。
- 动作类至少：idle/submitting/success/failed/unknown；提交中禁用重复点击。
- 未知就是未知，不伪装在线/离线；业务语义只从后端契约读。
- 前端状态（弹窗/tab/草稿/按钮）不等于后端事实（进程是否启动/消息是否送达/任务进度）。
- 禁止乐观改业务状态：点击启动只能显示“启动中”，等后端确认再显示“运行中”。

四、每个交互有后端依据
- 输出接口映射表：用户动作 → 页面 → 后端接口/方法 → 数据来源 → 状态 → 缺失备注。
- 没有接口的写「待补充」，不要虚构接口/数据。
- 内部接口、调试数据不包装成用户按钮。

五、组件与异步
- 每个组件考虑：loading/empty/error/success/unknown；分页/滚动；筛选/时间范围刷新；切页回来是否重取；卸载停请求；旧响应不覆盖新状态；重复提交。
- 页面布局、组件、Hooks、API 层、类型、Store 分层；不写巨大组件。

六、实时与轮询
- 明确哪些用 HTTP、WS/SSE、轮询、手动刷新。
- 不随意加 setInterval；统一数据更新层；页面隐藏/卸载停止；断线重连后拉快照；事件去重；请求带 generation。
- 超时/断线是 unknown，不是成功也不是失败。

七、视觉统一（科幻风）
- 深蓝黑背景、青/蓝强调、浅蓝文字；禁止整页纯白/纯黑突变。
- 统一颜色/字体/字号/字重/间距/圆角/阴影/图标/动效/组件库。
- 所有页面复用同一套 tokens 和组件，不每页重新发明。

八、工程与交付
- 不虚构数据；统一错误处理；错误要可见可行动（code/message/hint/retryable）。
- 防重复提交；处理生命周期；窗口缩放；可观测性；组件复用。
- 先输出：后端地图、功能地图、页面清单、接口映射表、状态矩阵、数据更新策略、视觉 tokens、分层方案、待补充清单。
- 最后再画页面。
```

## 10. 示例：记忆页接口映射（当前后端）

| 用户任务 | 后端依据 | 状态 |
| --- | --- | --- |
| 看当前记忆方式 | `kernel.memory.mode` / `settings.model()` 的 `memory.mode` | 已有 |
| 切换叙事/向量 | `settings.set('surfcore/kernel','memory.mode',...)` | 已有 |
| 看向量状态 | `kernel.memory.vectorStatus()` | 已有 |
| 看向量配置 | `kernel.memory.vectorConfig()` | 已有 |
| 编码待处理 | `kernel.flushVectors()` / `memory.encodePending()` | 已有（需 embedder） |
| 重建索引 | `memory.rebuildVectors({modelSpace})` | 已有 |
| 看模型索引列表 | `vectorStatus().spaces` | 部分（只有已有索引，不是已安装模型） |
| 记忆库搜索 | `memory.searchVector()` | 待补充（无 viewer 可见性过滤） |
| 最近记忆列表 | `memory.snapshot()` / `fullCard.recall()` | 部分（原始记录，需可见性投影） |
| 本地模型/运行时安装 | 无 | 待补充 |
| 云端 Provider/Key/测试 | 无（仅环境变量） | 待补充 |
| Host 实时接口 | 无 | 待补充 |

> 记忆页可以先做“方式 + 状态 + 编码/重建 + 设置”；记忆库、模型安装、Provider 测试等标「待补充」，不要先编接口。
