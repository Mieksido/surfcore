# 记忆卡（角色的长期记忆）设计与使用

> 角色卡管「她是谁」，记忆卡管「她记得什么」。
> 代码：核心引擎 `src/memory-card.js`；插件维护器 `plugins/surfcore/lib/memory-card.js`。
> 本文是记忆规则、容量规则、隐私边界与验证方法的唯一说明。

---

## 1. 和角色卡的区别

| | 角色卡（`roles/<角色>.md`） | 衰减记忆卡（`memory-card.*`） | 全量记忆卡（`memory-card-full.*`） |
| --- | --- | --- | --- |
| 内容 | 身份、性格、说话风格、称呼表 | B站冲浪、QQ 聊天、和主人的互动（会模糊/遗忘） | 同样的记忆，但**永久清晰、永不遗忘** |
| 变化 | 基本不变，只有用户要求才改 | 一直在变：新增、模糊、遗忘 | 只增不删；新记忆先进衰减卡，再归档 |
| 注入 | 每条 QQ 消息；B站每次醒来（压缩版） | **每条 QQ 消息 / B站每次醒来（按预算裁剪）** | **不注入**；只在控制台/API 里按需查看、搜索、召回 |
| 上限 | `role.maxInjectChars`（默认 6000 字） | `memoryCard.maxChars`（默认 0=无上限，警告 `warnChars` 默认 60000 字） | `memoryCard.fullMaxBytes`（默认 10GB；0 = 不限制，超过只告警） |

**平时只加载衰减记忆卡**：QQ 桥接只读当前角色的 `memory/memory-card-prompt-qq.md`，B站 调度器只读当前角色的 `memory/memory-card-prompt-bili.md`（角色系统见 [`CHARACTER_PERSONA.md`](CHARACTER_PERSONA.md)）；
全量卡**不生成任何 prompt 文件**，所以不会被自动塞进上下文。全量卡是「以后要查/加载全量记忆」的存档层。

**两张卡都会加载**（这里的“两张卡”是角色卡 + 衰减记忆卡）：QQ 桥接的角色提示 = 角色卡 + 管理员规则 + B站简报 + 衰减记忆卡；
B站 调度器每次醒来的统一上下文 = 人设卡 + 管理员 + 身份对齐 + QQ 脱敏近况 + 衰减记忆卡。

## 2. 文件与进程分工

| 文件 | 作用 | 谁写 |
| --- | --- | --- |
| `memory-card.json` | **唯一真相**：衰减记录、重要度、清晰度、告警状态 | 插件宿主（唯一写者） |
| `memory-card.md` | 完整、给人看的衰减卡（容量按它算） | 插件宿主 |
| `memory-card-prompt-qq.md` | 给 QQ 每条提示词的裁剪版 | 插件宿主 |
| `memory-card-prompt-bili.md` | 给 B站 每次醒来的裁剪版（隐私过滤后） | 插件宿主 |
| `memory-card-full.jsonl` | **全量存档**：一行一条、只追加；所有记录 `clarity=vivid`，不衰减 | 插件宿主 |
| `memory-card-full-stats.json` | 全量卡计数/字节数索引（容量按它算，不扫全档案） | 插件宿主 |
| `memory-card-full.md` | 全量卡人看版（导出/查看用） | 插件宿主 |
| `memory-inbox.jsonl` | 桥接 append 的原始 QQ 事件（最多 1MB，轮转 `.1`）；桌宠对话也追加到这里（`platform=pet`） | QQ 桥接 / 桌宠插件（只追加） |

- **QQ 桥接**（独立进程）不写卡：它只把「主人消息 / 直接对她说的话 / 有情绪的公开发言」追加到 inbox，
  并在每条提示词里读现成的 `memory-card-prompt-qq.md`（按 mtime 缓存）。
- **桌宠对话**（2026-10-25）：插件在每次 `/chat` 成功后追加两条事件（`platform=pet`：主人说的 / 她回的），
  维护器把回复并进 `pet-owner` 的 `botReply`；没有对应主人的主动搭话记为 `pet-self`。
  设置 → 桌宠 →「把桌宠对话写进记忆卡」可关；记忆卡总开关关掉时不写。
  桌宠记录 `platform=pet`、`scope=pet`，默认**不进 B站 注入块**；提示词里单独一段「## 桌宠（私下相处）」。
- **插件宿主**（DSH 进程）启动 8 秒后整理一次，之后每 10 分钟一次：
  摄取 inbox + `state/bili-memory.json` → **先归档全量卡** → 每日遗忘 → 超 100% 自动压缩 → 写输出 → 容量告警。
  「立即整理」的提示会分别报告新增 QQ / 桌宠 / B站 条数。
- **B站 调度器** 只读 `memory-card-prompt-bili.md`（mtime 缓存），不解析 JSON，也不读全量卡。
- 只有插件写卡，所以不存在两个进程同时改 JSON 的覆盖问题；桥接只 append。
- 写盘是原子写（临时文件 + rename）；每日整理前备份衰减卡；全量卡是 append-only JSONL，**不整份备份**（只备份很小的 stats 文件）。
- **归档时机**：`archiveDecayedToFull()` 在衰减/压缩/遗忘**之前**执行，只 append 新行到 `memory-card-full.jsonl`；
  衰减卡记录追加成功后才写 `fullArchivedAt`，避免「标记了但没写进去」。全量卡只增不删。
- **QQ 对话记两边**：桥接既写主人/群友消息，也写她自己的出站消息（`isSelf`）。
  插件优先把她的回复并进最近一条主人记录（`botReply`，渲染成「主人：… → 她回：…」）；
  找不到对应主人记录时（例如群聊主动发言）才单独生成一条 `qq-self` 记忆。

## 4. 重要度评分（「特殊判断规则」）

评分在 `scoreMemory()` 中实现，纯函数、可单测。**没有调用模型**，所以结果稳定、可解释、可回滚。

| 信号 | 加分 | 说明 |
| --- | --- | --- |
| 基础 | +8 | 任何一条记录 |
| 主人私聊 | **+42** | `ownerQQ` 的私聊消息 |
| 主人在群里说话 | **+32** | 仍是主人，但公开场合 |
| 直接对她说 | +8 | @ / 引用 / 私聊 |
| 情绪浓度 | **+0~24** | 「喜欢/想念/难过/委屈/哭/抱抱/对不起/谢谢/陪/永远…」强词 8 分/个，普通情绪词 3 分/个，感叹号 1 分 |
| 第一次 / 最早 | **+30** | 命中「第一次/初次/头一次/最早/刚认识/纪念日…」；和主人相关时直接 100 分并置顶 |
| 约定 / 承诺 | +16 | 「答应/约定/说好/以后/下次/记得/不要忘/发誓」 |
| 矛盾 / 道歉 / 和好 | +14 | 「吵架/生气/道歉/对不起/和好/误会/冷战」 |
| 关于自己 | +5 | 「我喜欢/我是/我的…」 |
| B站 打分 | +0~18 | 她在 B站 给视频打的分（高分说明真喜欢） |
| 收藏 | +8 | 公开收藏 |
| 日记里写过 | +4 | 说明这件事在 B站 那边留下了印象 |
| 太短 / 信息量低 | −12 | 少于 6 个字符 |

- 最终夹在 1~100。
- `pinned`（永久锚点）规则：第一次和主人说话；任何命中「第一次」且重要度 ≥60 的事；管理员手动置顶。
- `minOwnerImportance`（默认 65）：主人相关且重要度达到此值的记忆**永远不会被遗忘**，最差保持「清楚」。

> 调参只改 `src/memory-card.js` 的权重；改完跑 `npm run test:memory-card`。

## 4.5 「最初」与「初次相遇」（**独立于「重要」**）

「最初」不是重要度的一部分，而是另一套判断：

- **只算和主人（管理员）的互动**；B站 视频、群友消息、手动记忆都不会被标为「最初」。
- 时间窗口 = **第一次主人互动起的 30 天**（`firstOwnerAt`）。`initialProbabilityForOffset()`：

| 距首次主人互动 | 概率 | 档位 |
| --- | --- | --- |
| 0–9 天 | **0.90** | `first10` |
| 10–19 天 | **0.55** | `mid10` |
| 20–29 天 | **0.30** | `late10` |
| ≥30 天 | **0.03** | `after` |

- 概率是**确定性**的：用记录 id 做稳定散列，不会每次刷新随机变；同一张卡重复读取结果一致。
- 标记为「最初」的记忆有保护：**最差保持「清楚」，不会被彻底遗忘**；也不参与容量压缩/条数淘汰。
- 渲染时「最初」单独成区：`## 初次相遇（和主人）`、`## 最初的日子（和主人）`，不与「重要」混在一起；
  「重要」仍按原来的重要度规则独立计算。

**初次相遇**：

- 默认自动取**最早一条主人互动**；它会被固定（pinned）、重要度 100，并进入「初次相遇」区。
- 管理员可以在「记忆」页勾选一条 → **设为初次相遇**；
- 勾选多条 → 合并成**一个事件记忆**（`和主人的初次相遇`，保留每条的日期和正文摘要）；
  原记录从衰减卡移除，但全量卡已先归档保留。
- 「恢复自动」会取消手动指定，回到最早一条主人互动。
- 只能选带 `owner` 标记的记录；非主人记忆不能设为初次相遇。
- **初次相遇永远排在记忆列表最顶**；其他置顶记忆排在它后面（同为置顶再按最近活动/重要度）。

**普通记忆合并（只合并，不设初遇）**：

- 在「最近记忆」里勾选**任意 ≥2 条**记忆 → **「合并为一个事件」**；
- 可填事件标题（默认取第一条标题），可选 **「合并后置顶」**（默认开，方便之后管理）；
- 原记录从衰减卡移除，但全量卡已先归档保留；合并结果是一个普通事件记忆，**不会改变初次相遇**；
- 同一事件会继承被合并记录的重要度上限、标签和平台；如果混合了 QQ 私事，事件的 scope 会收紧为 `qq`，不会进 B站 提示词；
- 「初次相遇」记录不允许直接合并（会留下失效的初次相遇元数据），需要先点「恢复自动」。

## 5. 清晰度与遗忘（像人一样）

四档清晰度，每天最多降一档（所以是「慢慢模糊」而不是一次性删除）：

```
清晰 vivid → 清楚 clear → 模糊 fuzzy → 只剩印象 trace → 遗忘（记录删除）
```

每天的目标清晰度由 `targetClarity()` 计算：

```
retention = importance
          + min(12, recallCount × 2)
          + 最近加成（7 天内 +18；2 天内被提到 +8）
          − 时间惩罚（超过 fuzzyAfterDays 后，每天 −0.35；主人重要记忆每天只 −0.12）
```

- `recentDays`（默认 7）内：至少「清楚」。
- `pinned` / 第一次：永远「清晰」。
- 主人重要记忆（≥ `minOwnerImportance`）：retention 有 55 的下限，永远不会跌到「只剩印象」以下。
- 超过 `forgetAfterDays`（默认 60 天）且重要度 <50 的非主人记忆 → 目标直接是「遗忘」，
  但仍然每天只走一档，走完 `清楚→模糊→印象→遗忘` 才真正删除。
- 被再次提到会更新 `lastSeenAt` / `recallCount`，第二天可能回升一档（复习效应）。
- 每日整理在 `dailyHour`（默认 4 点）之后的第一次 tick 执行；同一天只跑一次。
- **补跑**：如果 DSH 关了好几天，下一次整理会按错过天数连续降档（最多 30 天），不会因为停机就停止遗忘。
- 注意：上面「每天一档」是**每日衰减**；容量压缩（手动或满 100% 自动）会在一次操作里连续降档，直到回到目标容量。两者都遵守「不动置顶 / 主人重要记忆」。

**遗忘是删除正文**，只保留 `stats.forgotten` 计数；不会把「已忘」的内容继续喂给模型。

## 6. 容量与告警（80% / 90% / 100%）

- **容量** = 完整 `memory-card.md` 的字符数（含标题、分区、记录行）。
- 上限 `maxChars` 默认 **0 = 无上限**；正数只是软上限，不再限制到 100000。无上限时用 `warnChars`（默认 60000）在 80/90/100% 只告警。
- 三档告警：`≥80%` 提醒、`≥90%` 严重、`≥100%` 已满。
- `≥100%` 且 `autoCompact=true`：自动压缩到 90%，但**告警仍按 100% 保留**（用户仍能看到「刚满过」）。
- 告警出口：
  1. DSH 设置 → SurfCore：页面每 60 秒查一次，80% 以上直接弹窗（立即压缩 / 2 小时后再提醒 / 本次不再提醒）；
  2. 「记忆」页顶部永远有容量条与警告框；
  3. 可选：QQ 私聊管理员（`notifyOwner`，同一档 12 小时一次；桥接侧还有 10 分钟节流）。只发给 `ownerQQ`，不发群。
- 压缩不会动 `pinned` 和主人重要记忆（≥ `minOwnerImportance`）；只把「不重要 → 老 → 已经模糊」的记录一档一档降级。
- **全量卡另有一套上限**：`fullMaxBytes` 默认 10GB（0 = 不限制）、`fullMaxRecords` 默认 0（不限制）。
  超过只在控制台告警，**绝不自动删除、压缩或模糊**——全量卡是“全量”的，宁可提示导出/备份。
- 全量卡存储是 **append-only `memory-card-full.jsonl`**（一行一条，只追加）+ `memory-card-full-stats.json`；
  10GB 级档案不会整份读入内存、不会每次维护重写；容量按 JSONL 实际字节数算，不靠渲染整份 md。
- 控制台「记忆」页顶部明确标注 **当前提示词加载：衰减记忆卡**；全量卡面板标注 **未加载到提示词**。

## 7. 隐私边界（不可关）

| 规则 | 实现 |
| --- | --- |
| 私信/私聊永不跨平台 | QQ 记录 `scope='qq'`；B站 注入只取 `scope='bili'/'shared'` |
| 桌宠对话默认不进 B站 | 桌宠记录 `scope='pet'`；B站 `visibleFor` 只放行 `bili/shared`（或显式 `includeQqInBili` 的 QQ） |
| 桌宠对话可关 | 设置 → 桌宠 →「把桌宠对话写进记忆卡」；总开关 `memoryCard.enabled=false` 时也不写 |
| B站 默认不带 QQ 记忆 | `includeQqInBili` 默认 `false`；即使打开，也再次脱敏 5~12 位数字 |
| QQ 号/群号/B站 mid 不进共享正文 | `redactForMemory(text, {scope:'shared'|'bili'})` |
| 密码/token/密钥/手机号/证件号/链接 | 入库前统一脱敏（`[已隐藏]` / `[手机号已隐藏]`） |
| 时政/娱乐圈内容 | 标记 `sensitive`，只留在本地完整卡，不进 B站 提示词 |
| 不读私信文件 | 桥接只 append 白名单群消息与主人消息；inbox 不含媒体、命令 |

> 记忆卡是写进**提示词**的，所以它比普通日志更敏感：任何新增字段都必须过一遍脱敏。

## 8. 配置（`~/.dsh/surfcore/config.json` → `memoryCard`）

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | true | 关掉后不再摄取，并清空两份注入块（文件保留） |
| `maxChars` | 0（无上限） | 整张卡字数软上限；0 = 不限制 |
| `injectMaxChars.qq` | 2200 | 每条 QQ 提示词最多带多少记忆 |
| `injectMaxChars.bili` | 2000 | B站 每次醒来最多带多少记忆 |
| `recentDays` | 7 | 最近 N 天保持「清楚」 |
| `fuzzyAfterDays` | 7 | 新记忆保护期 |
| `forgetAfterDays` | 60 | 不重要记忆最早可以彻底遗忘的天数 |
| `dailyHour` | 4 | 每天几点后执行遗忘整理 |
| `minOwnerImportance` | 65 | 达到这个值的主人记忆永不遗忘 |
| `autoCompact` | true | 满 100% 自动压到 90% |
| `notifyOwner` | true | 容量告警私聊管理员 |
| `includeQqInBili` | false | B站 提示词是否带 QQ 记忆（隐私红线，默认关） |
| `maxRecords` | 600 | 衰减卡 JSON 记录条数上限 |
| `fullMaxBytes` | 10GB | 全量卡硬上限（按 JSONL 字节数；0 = 不限制，超过只告警） |
| `fullMaxRecords` | 0 | 全量卡记录条数上限（0 = 不限制） |

控制台「记忆」页可直接改这些字段（保存后立刻重渲染注入块）：
- **衰减卡字数上限**在容量条下方直接输入（0 = 无上限，正数 = 软上限）；旁边是**容量警告字数**（默认 60000，0 = 不告警）；
- **全量卡上限**按 GB 输入（默认 10GB，填 0 = 不限制）。

## 9. API（插件宿主，本机回环 + 控制台令牌）

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/dsh-surfcore/api/memory-card` | 状态 + 完整卡 + 两份注入块 + 记录 + 备份 |
| POST | 同上 `{action:'maintain'}` | 立即摄取 + 按需遗忘 + 按需压缩 |
| POST | 同上 `{action:'compact', targetRatio:0.8}` | 手动压缩 |
| POST | 同上 `{action:'pin', id, pinned}` | 置顶 / 取消 |
| POST | 同上 `{action:'forget', id}` | 忘记一条（置顶不允许） |
| POST | 同上 `{action:'ack', level}` | 确认容量告警 |
| POST | 同上 `{action:'add', text, importance, scope}` | 管理员手动记一条 |
| POST | 同上 `{action:'set-first-meet', ids:[...]}` | 指定一条 / 多条合并为「和主人初次相遇」 |
| POST | 同上 `{action:'clear-first-meet'}` | 取消手动指定，恢复自动（最早一条主人互动） |
| POST | 同上 `{action:'restore', name}` | 从备份恢复衰减卡 |
| GET | `/dsh-surfcore/api/memory-card/full?q=&limit=` | 全量卡状态 + 完整 md 预览 + 关键词召回（**只读**） |
| POST | `http://127.0.0.1:<consolePort>/api/memory-card/notify` | 桥接只私聊管理员（插件告警用） |

QQ 桥接侧还有：

- 角色提示 / 二代唤醒提示 / `qq_get_prompt` 的 `memoryCard` 字段都读同一份 `memory-card-prompt-qq.md`。
- 全量卡没有对应的 prompt 文件，所以桥接/调度器**没有**加载全量卡的代码路径；以后要接「按需加载全量片段」，
  从 `/memory-card/full?q=` 或 `recallFullMemory()` 取，不要改成常驻注入。

## 10. 怎么验证

```bash
npm run test:memory-card      # 规则引擎：评分 / 遗忘 / 压缩 / 容量 / 隐私 / 全量归档 / 幂等
npm run test:memory-card-wiring

cd plugins/surfcore && npm test   # 含 test-memory-card-api.mjs（临时 DSH_HOME）
```

手动：

1. DSH 设置 → SurfCore → 记忆：顶部应明确写「当前提示词加载：衰减记忆卡（日常加载）」；
   下面应看到「记忆卡」容量条、最近记忆、QQ/B站 注入预览，以及「全量记忆卡（只存档）」面板；
2. 点「立即整理」→ 状态里应出现新增 QQ / B站 / 全量归档条数；全量面板应出现 `memory-card-full.jsonl` 的记录；
3. 把 `maxChars` 临时调到 2000（或把 `warnChars` 调到很小）→ 容量条变黄/红并弹窗；点「立即压缩到 80%」→ 容量回落；
4. 在全量面板搜一个刚被衰减卡遗忘的词 → 应能搜到原文（全量卡不参与提示词）；
5. 真机发一条主人情绪消息（例如「今天有点难过」）→ 下一条 QQ 提示词里应出现「和主人（管理员）的记忆」；
6. B站 醒来时看提示词：应有 `【记忆卡 · 你自己的记忆】`，且**不含** QQ 私聊内容、**不含全量卡**；
7. 在「最近记忆」勾选一条主人互动 → 「设为初次相遇」→ 顶部初次相遇变「手动指定」；
   勾选多条再设一次 → 原始记录消失、出现一条 `和主人的初次相遇` 事件；点「恢复自动」→ 回到最早一条。
8. 勾选任意两条非初次相遇记忆 → 「合并为一个事件」（可填标题）→ 原记录消失、出现一个默认置顶的合并事件；
   顶部初次相遇不变。

## 11. 已知边界

- 「重要度」是启发式，不追求 100% 准确；边界靠容量/隐私硬规则，不靠评分。
- 「最初」的 30 天窗口从**记忆卡里已知的第一条主人互动**开始；更早的历史不会自动回溯。
  概率是确定性的“抽签”，所以前 10 天也不是每一条都会标成最初（约 90%），这正是“概率最大”的含义。
- 全量存档里的「最初/初次相遇」标记反映**归档当时**的状态；之后重新指定初次相遇，只更新衰减卡，不会重写历史 JSONL。
- 「第一次和主人说话」锚点从**启用记忆卡后的第一条主人消息**开始；更早的历史不会自动回溯
  （DSH 会话日志是压缩格式，且有隐私边界）。需要补更早的锚点，请在「记忆」页手动记一条并点「置顶」。
- 模糊化是**确定性截断 + 标签归纳**，不调用模型做摘要（可控、免费、可测试）；以后若接模型摘要，必须保留原文备份与回滚。
- B站 的 `bili-memory.json` 由桥接生成；桥接没跑时 B站 记忆不会更新，但已有记忆卡照常注入。
- QQ 记忆默认不进 B站；如果用户打开 `includeQqInBili`，仍会脱敏数字，但仍建议只用于「公开群聊」场景。
- **全量卡只从启用本功能之后开始归档**：之前已经被衰减卡忘掉的记忆无法凭空恢复；当前衰减卡里还存在的记录会在首次维护时全部补档。
- **全量卡不自动加载**：这是设计约束，不是遗漏。以后若要「按需加载全量片段」，应走 `/memory-card/full?q=` / `recallFullMemory()`，
  只把命中的几条注入当前回合，不要常驻注入整张全量卡。
- **全量召回是流式扫描**：默认只扫档案末尾 200MB（`maxScanBytes`），避免一次 10GB 查询把机器拖死；
  真要全 10GB 检索，后续需要倒排索引/分片（当前未实现）。最近的记忆从文件尾部读，不受影响。
- **全量 md 只在档案 ≤5MB 时生成**；更大的档案只保留 JSONL + stats，避免再复制一份 10GB 的 markdown。
- **全量卡包含所有本地记忆（包括 `sensitive` 标记的时政/娱乐内容）**，只存在本机、不进提示词；导出/分享前请自行检查隐私。
