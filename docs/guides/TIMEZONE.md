# 自定义时区

> 配置项：`config.json` 的 `timezone`（也可用环境变量 `SURFCORE_TIMEZONE`）。留空 = 跟随系统时区（旧行为，完全不变）。
> 代码：`src/timezone.js`。测试：`scripts/test-timezone.mjs`。

## 为什么需要

很多云服务器的系统时区是错的，甚至是默认 UTC。SurfCore 里这些都是按「本地时钟」算的：

| 功能 | 受影响的表现 |
| --- | --- |
| 目的机制 / 主动搭话的**安静时段** | 半夜 3 点（你的时间）她来找你 |
| **每日 token 额度** 换天、唤醒上限、鱼群守则的「今天」 | 额度在下午 4 点清零 |
| B站 **作息窗口** / 生物钟 / 四类动态时段 | 窗口整体错位 8 小时 |
| 早安问候、B站每日分享的**定点时间** | 08:00 的问候在 16:00 发 |
| 记忆卡每日衰减、日志时间戳、提示词里的「现在是…」 | 她以为现在是另一个时间 |

不想（或不能）改服务器系统时区时，在 SurfCore 里单独设一个就行，只影响 SurfCore，不碰系统和 DSH。

## 怎么设

**设置页**：DSH → 设置 → SurfCore → 概览 → **时区**。上面会同时显示「系统时区」和「SurfCore 使用」各自此刻的时间，一眼看出系统时区对不对。保存后插件立即生效，桥接约 1 分钟内自动跟上（**不用重启**）。

**配置文件**：

```jsonc
{ "timezone": "Asia/Shanghai" }
```

**环境变量**（优先于文件，适合容器 / 临时试）：`SURFCORE_TIMEZONE=Asia/Shanghai`。

可填的值：

- IANA 时区名：`Asia/Shanghai`、`America/New_York`、`Europe/London`、`UTC`……（大小写不敏感，自动规范）；带夏令时的地区会正确处理。
- 整点偏移：`UTC+8`、`GMT-5`、`UTC+08:00`。半小时偏移的地区（印度 +5:30 等）请用 IANA 名（`Asia/Kolkata`）。
- 留空：用系统时区。

填错会怎样：设置页保存时直接报错并给出建议（HTTP 400 `invalid_timezone`，带 `hint`），不会存进去；
如果是手改 `config.json` / 环境变量填错了，SurfCore **回退系统时区**，并在桥接日志和设置页里红字提示，不会崩。

## 生效范围与重启

| 进程 | 怎么生效 | 改了之后 |
| --- | --- | --- |
| QQ 桥接（`src/bridge.js`） | 启动时把配置的时区设成进程时区（`process.env.TZ`），之后每分钟复查 | 约 1 分钟内自动跟上，日志会打一行 `时区：…` |
| B站 CLI 工具（`tools/bili.mjs` 起的子进程） | 起子进程时带上 `TZ` | 下一次调用即生效 |
| DSH 里的插件（调度器、桌宠、记忆卡…） | 涉及本地时钟的函数用 `withConfiguredTimeZone()` 包住：同步地临时切、算完立刻还原 | 立即生效 |

## 设计取舍

- **为什么不直接在所有进程里设 `process.env.TZ`？** 插件跑在 DSH 宿主进程里，那不是我们的进程，常驻改它的时区会影响宿主和别的插件。所以宿主里只在 SurfCore 自己的计算期间**临时**切换（JS 单线程，同步块不会被打断；`fn` 里不能 `await`）。自己拥有的进程（桥接、CLI）则直接常驻，其内部几十处 `getHours()` 之类的调用一行都不用改。
- **为什么不自己写一套带时区的日期运算？** 「几点换天」「下一个 08:30」「夏令时跳变」用原生 `Date` 在目标时区下算最不容易错；自己重写要覆盖 `setHours(+1 天)` 之类的全部边界。
- **还原为什么要显式设回系统时区？** `delete process.env.TZ` 不会让 V8 重新读系统时区（测过：删了之后仍停在上一个时区），必须先 `TZ=<系统时区>` 再删变量。这条在测试里钉住了。
- **目的引擎保持零 import**：它通过 `setClockScope()` 由宿主注入时区作用域（插件的 `pet-purpose.js` 注入 `withConfiguredTimeZone`），不破坏它「可原样抽成独立模块」的边界。
- **设置页浏览器端显示的时间**（日志列表等 `toLocaleString`）仍是浏览器本机时间——那是你自己电脑的时钟，不是服务器的。

## 已知边界

- 已经排好的「定点任务」（例如已排定的下次问候）在换时区后，按下一轮重新计算的结果为准，不会回头改已发生的。
- MCP server 进程（QQ 工具 / SnowLuma 探活 / 联网搜索）不含本地时钟逻辑，未处理。
- `TZ` 环境变量被用户自己设置过时（如系统层面 `TZ=Asia/Tokyo`），清空 `timezone` 会还原成启动时的样子。
