# 报错与建议规范（ERROR REPORTING）

> 2026-10-29 用户要求（刚性）：**每次修 bug / 加功能，都要把「失败时用户看到什么」当成交付的一部分**；
> 不容忍静默错误。本文是判据与模板，AGENTS 1.7 是硬规则。
> 触发场景：任何新增/修改的接口、按钮、后台任务、安装/启动流程。

## 一、三条硬要求

1. **看得见**：失败必须出现在用户正在看的那个界面（弹窗 / 页面红字 / 状态点 / toast 至少一个）。
   写进日志、只 `console.error`、只返回 `{ok:false}` 而前端不展示 —— 都算没做。
2. **说清楚 + 给下一步**：文案回答三件事——**在哪失败**（哪个路径/哪个服务）、**为什么**（能判断的话）、
   **现在该点什么**。能自动恢复的给「重试」；不能的给「打开下载页 / 去某个设置 / 联系作者」。
3. **失败分支有测试**：新增失败路径时，至少一条断言钉住 `code`、`hint` 非空、关键信息在错误里
   （本次示例：`plugins/surfcore/scripts/test-snowluma-install.mjs` 第 4 节）。

## 二、接口返回格式（`ok:false` 时）

```json
{
  "ok": false,
  "code": "snowluma_not_found",        // 机器可读，稳定不改；前端据此决定弹窗/文案
  "title": "没找到 SnowLuma",           // 弹窗标题（短）
  "error": "常见位置里都没有 SnowLuma",  // 人读：发生了什么
  "hint": "点「浏览…」选根目录；还没装就点「打开官方下载页」",  // 下一步（必须可执行）
  "tried": ["C:/...", "D:/..."]         // 可选：诊断信息（路径/端点/尝试次数）
}
```

- **只加不改**：新字段可以加；已有的 `error` 语义不要改（老前端只读它）。
- **不要用 200 假装成功**：`ok:false` 就是失败；HTTP 状态按语义（400/403/404/409），
  控制台老接口习惯 200+ok:false 的保持兼容，但**前端必须读 `ok`**。

## 三、前端：弹窗还是 toast

| 场景 | 用什么 | 判据 |
| --- | --- | --- |
| 用户必须做选择（重试/浏览/下载/关闭） | **弹窗**（`ErrorModal`） | 失败阻断了主流程，toast 会飘走 |
| 瞬时提示、可自动恢复（保存成功、已取消） | toast | 用户不需要行动 |
| 后台轮询/心跳失败 | 状态点 + 可查日志 | 不打断用户，但状态栏必须变红/变灰 |
| 表单校验 | 字段下方红字 | 与输入绑定 |

**弹窗最低要素**：标题（哪里错）、正文（发生了什么）、`hint`（下一步）、至少一个行动按钮 + 关闭；
诊断信息折叠在 `<details>` 里，别糊一屏。

参考实现：
- 组件：`plugins/surfcore/lib/client.js` · `ErrorModal`
- 结构化报告：`plugins/surfcore/lib/snowluma-install.js` · `snowLumaMissingReport()`
- 接线：`handleBridge` 的 `detect-snowluma`（失败返回 `code/title/error/hint/tried`）+ 概览「检测」按钮

## 三·五、跨层契约：别再让"传值/传函数"错位

2026-10-29~30 连续三起同类事故，都是**一层以为传的是 A，另一层收到的是 B**：

| 事故 | 一层以为 | 实际 |
| --- | --- | --- |
| 语音页保存报 `toast is not a function` | 传了通知函数 | 传的是浮层文案字符串 |
| 管理员称呼仍叫「管理员」 | 保存时把称呼写进了配置 | 只投影了 ownerQQ，桥接读不到 |
| 改了语音开关模型仍没工具 | 改开关即生效 | MCP 工具表是进程启动快照 |

**三条硬规则**：

1. **同名不同物必须改名**：状态叫 `toastText`，函数叫 `notify`，禁止一个 `toast` 既是字符串又是函数。
2. **成功路径上的界面失败，不得改写业务结论**：保存成功之后的通知/刷新失败，只能提示"已保存（界面提示失败）"，不能变成"保存失败"。
3. **跨进程/跨层的数据，必须显式投影并校验**：配置从 A 写到 B，要有测试断言"B 真的能读到"；启动快照类数据，要写明"改完需重启"或改成调用时判定。

**禁止清单（新增）**：

- ❌ 把字符串/对象当函数传（`toast(...)`、`cb(...)`）而不做 `typeof === 'function'` 断言；
- ❌ 在 `catch` 里把"通知失败"和"业务失败"混成同一个文案；
- ❌ 只写一端、指望另一端自动读到（跨进程配置必须显式投影 + 读回断言）。

**测试要求**：契约类 bug 至少加一条**源码级断言**（例如"所有 Tab 的 toast 必须是 notify"），因为这类错误运行时才炸、review 很难肉眼发现。

## 四、禁止清单

- ❌ `catch {}` / `catch (e) { console.log(e) }` 之后流程继续，用户以为成功；
- ❌ 前端收到 `ok:false` 只 `toast` 一句「失败」，没有下一步；
- ❌ 错误文案让用户「去另一个页面找设置」（兜底必须出现在失败提示的同一个界面里，见 PITFALLS #80）；
- ❌ 返回 `error` 但不说清楚是哪个路径/哪个服务；
- ❌ 新接口失败分支没有任何测试。

## 五、交付自检（写进 case 的「验证」段）

- [ ] 失败时用户看到什么？（截图/文案/按钮）
- [ ] `code` 稳定吗？前端按它做什么？
- [ ] `hint` 里的动作真的能点/能照做吗？
- [ ] 失败分支有断言吗？
- [ ] 有没有只写日志、不展示的路径？
