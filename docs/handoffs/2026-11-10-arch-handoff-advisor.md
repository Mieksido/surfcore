## 0. 一句话背景

在**不碰旧仓库**的前提下，用新架构（内核 + 大适配器 + 平台包）复现旧 SurfCore 的能力。
硬约束（用户定的，已冻结）：

1. **接口结构不许动**（三种消息、包的四块+收/发、内核 5 个方法、读取器输出形状）；
2. 动**接口内容**必须先提示，并说明改的是「大适配器」还是「某个模块的小适配器」；
3. 旧代码是**需求**不是骨架；旧仓库只读；
4. 合规：第三方运行时**不随包分发、不程序化部署**。

### 1.2 一次对话的链路（现在真能跑）

```
包收 → 白名单（门外）→ 合批（8s/12条）→ 内核入库（全量卡+衰减卡+向量，三处写）
  → 唤醒判断（分级+轮次守卫）→ 读记忆（只走一条，统一 {text,refs,mode}）
  → 提示词（人格 + 【群里的词】+【刚才】+【对方发来的】+【现在】）
  → 上下文预算（人格不剪 → 剪记忆 → 剪正文）→ 模型 → 工具面 → 意图
  → 收尾判定（可能补 close 意图）→ 表情挑图（mediaId→路径）
  → 语音闸门（合成则转 send_media audio）→ AI 标识事实
  → 大适配器：幂等/能力门 → 包真发 → 回执 → 审计
```

### 1.3 关键位置约定

| 判断类型 | 放哪 | 例子 |
| --- | --- | --- |
| 关于"她"的判断 | 内核 | 记不记、说不说、用不用语音、该不该收尾、挑哪张表情 |
| 关于"怎么运"的机械动作 | 大适配器 | 幂等、重试、脱敏、装包、白名单 |

## 3. 工作准则（我实际在守的）

### 3.1 用户给的 18 条（逐条都落成了检查）

边界/职责分离 · 功能放对层 · 减少耦合 · 按秘密切分 · 减少跨边界消息 ·
接口格式统一 · 稳定不依赖易变 · 依赖不成环 · 稳定必抽象 · 不拿复杂字段当公约 ·
业务不认识外部世界 · 假适配器隔离测试 · 结构简内容繁 · 单写者 · 可单独测 ·
不启动世界能验证 · 适应度函数 · 规则进日常流程。

### 3.2 我用自动检查守住的（不是靠自觉）

| 检查 | 守的是什么 |
| --- | --- |
| `fitness` | 内核/运行时零渠道名；5 条依赖方向；每层有测试 |
| `audit` | 编码损坏（含文档）、占位符、库代码 console、重复导出、import 解析、死导出、模块加载、**静默测试（缺 process.exit）** |
| `core-check` | 本体无二进制、不 import 扩展、无渠道名、不含平台包 |
| `capability-map` | 登记表 ↔ 真实代码：漏登记/路径不存在/done 没证据 → 红 |
| `legacy-map` | 基线 mappedTo 必须指向真实模块 |
| pre-commit hook | 只对架构路径触发；不过不许提交 |

### 3.3 我给自己加的纪律

- **每个模块只做一件事**，秘密写在文件名里（decay-card / full-card / turn-guard / outbox…）；
- **新增模块必须登记能力清单**（路径 + 角色 + 依赖谁 + 不许依赖谁 + 每条能力带状态与证据）；
- **动接口内容必须报**：改的是大适配器还是小适配器 + 人话解释；
- **失败必须可见**：降级、拦截、超时、合成失败都进审计，不假装成功。

## 4. 关键取舍（欢迎否）

| # | 取舍 | 我的理由 |
| --- | --- | --- |
| 1 | 合批放在**组装层**（app），不放内核 | 合批是运送节奏，不是"她怎么想"；内核只该收到"一轮" |
| 2 | 合批把多条并成**一条记忆** | 换来"不刷屏"；代价是记忆粒度变粗（已知并记录） |
| 3 | 语音合成成功 → 意图从 `say` 转 `send_media(audio)` | 包早就会发音频，不用改包；**意图种类没新增** |
| 4 | 白名单只管 `group:`/`private:`，其它渠道返回 `not-governed` | 终端等本地渠道不该被 QQ 的名单管；不是放水，是把管辖范围说清 |
| 5 | 工具层放包内，内核只说 `act` | 包若声明 42 个工具，内核不认识其中任何一个 |
| 6 | 全量卡**入库即写**，遗忘只从衰减卡出去 | "全量"就该全量；遗忘是衰减卡的语义 |
| 7 | 模型失败：临时故障说一句人话，永久故障沉默 | 说也没用时说话只会让人困惑 |
| 8 | 收尾用现有 `close` 意图，不新增 | 结构冻结；判断在内核，发送在包 |

## 6. 想请顾问会回答的问题

**A. 切分是否合理**
1. 内核现在有 10 个子块（记忆/目的/时机/表达/对话/收尾/黑话/表情/语音/支撑）。有没有该合并的（比如"对话"与"收尾"）、或该再拆的？
2. `kernel/index.js`（382 行）是唯一的总装点。它还该不该更薄？如果薄，哪些逻辑应下沉到子模块？

**B. 记忆模型**
3. 现在 ingest 一次写三处（全量卡、衰减卡、向量库）。旧代码"两套存储都在写、只读一条"是否要求**只写被读的那条**？我选了"都写"，对不对？
4. 全量卡入库即写、遗忘只从衰减卡出去 —— 这与旧的"全量卡"语义一致吗？

**C. 意图与工具**
5. 语音成功时 `say → send_media(audio)`，会不会让"她说了话"在回执/统计上不可区分？是否该保留 `say` 并在媒体里附语音？
6. 42 个渠道工具走 `act` + `args` 透传，会不会变成"拿复杂字段当公约"？是否该把工具声明收进内核工具面（现在内核只认 5 个通用工具）？

**D. 落位**
7. 合批放组装层、白名单放运行时 —— 这两个位置对不对？
8. 媒体理解（把图片/语音写成一句话）放表达层，对不对？还是该由平台包先写好再上报？

**E. 工程**
9. 审计现在只在内存（上限 500 条，不落盘）。要不要落盘（单写者）？
10. 能力清单和旧基线是两套数据源。是否该把"旧基线 → 新模块"的映射并进能力清单，只留一份？

**F. 优先级**
11. 下一步该先补：真模型 / 真语音 / 控制台 / 剩余 21 个工具 / 合并转发（需给媒体加 `forward` 种类，属内容变更，我还没做）。你的排序是？
