## 1. 一句话：我们在做什么

**从一张"适配器形状"出发，把 SurfCore 全部功能重新长成一个干净架构，而不是在旧代码上打补丁。**

- **内核**（当前阶段定义）：**记忆 + 目的机制**。
- **适配器**：一切外部世界（QQ / B站 / 桌宠 / 终端 / 未来任何东西）。
- **关系**：内核不认识任何渠道名；适配器不认识记忆。

**这不是"另起一个项目"，是"同一批功能换一副骨架"。** 所以你的功能知识不可替代。

## 2. 已经拍板的决定（请不要再重新讨论，除非有硬证据）

| # | 决定 | 理由（一句话） |
| --- | --- | --- |
| 1 | **旧架构是「需求」，不是「骨架」** | 旧代码只用来回答"有什么不能丢"，不用来决定新架构长什么样 |
| 2 | **分阶段：先形状，后契约** | 字段级的约定等某个模块真正接入时才写；提前写就是替未来拍板 |
| 3 | **契约是中心，两侧重新生长** | 不接受"把契约挂在现有 ExtensionHost 上"——那会继承"扩展是自己人"的错误假设 |
| 4 | **适配器形状**：四块（身份/能力/菜单/生命）+ 三管（上行事件/下行意图/上行回执） | 能力用"六条轴"定位而不是列清单，新平台不用改内核 |
| 5 | **身份 = 发布人 + 名字 + 版本**（展示成 `发布人@版本`） | 同一个名字不同发布人 = 两个不同适配器，信任等级不同 |
| 6 | **记忆双模块**：叙事 + 向量，**两套都存，只选一个读** | 这是老代码已有的语义（`memory.mode` 只影响读取） |
| 7 | **叙事是兼容层，迟早淘汰；向量是长期方向** | 用户明确：叙事效果太差，留着只为照顾部分用户 |
| 8 | **记忆只在她做出行为前读取**（不是每条消息都读） | 刷屏的群不会因为"每条都检索"而烧钱 |
| 9 | **两个读取器输出格式必须统一** | 否则上层又会长出 `if (mode === 'vector')` |
| 10 | **目的机制共用同一个读取接口**，不另起接口 | 一个读函数，多个调用方；读是只读的，多一个不影响 |

## 4. 为什么需要你（你不可替代的地方）

**因为"不漏模块"和"不漏行为"是两件事。**

我们已经把 112 个模块逐个归位了（`ARCHITECTURE-FROM-CONTRACT.md` §5），这部分我们有把握。
**但我们保不住"行为"**——比如这些全都写在代码注释里、而不是模块名里：

| 旧代码里的行为细节 | 出处 |
| --- | --- |
| 单实例锁里 **EPERM 不能当成"已有实例"**（否则锁文件里的 PID 被回收后桥接永久起不来） | `bridge.js` 的 `acquireLock` |
| 只读降级时**必须返回失败**，不许假装成功（否则"已保存"→重启全丢） | `bridge.js` 的保存接口 |
| **沉睡观察必须真等够**静默窗口，不能靠总时长凑 | 桥接的 `preSleepWait*` |
| 记忆**每天最多降一档**、被提到**升一档**、"最初"是独立于"重要"的保护 | `memory-card.js` |
| 目的机制**投递出去就先占今日次数**（模型回合已经花钱了） | `purpose-engine.js` 的 `markPurposeDelivered` |

**这些只有你知道。** 我们的行为清单（16 条）是从代码里挖的，但一定不全。
