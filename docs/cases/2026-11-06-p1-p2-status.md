## P1（需要排期，但不影响即时可用性）

### P1-1 更新看门狗复位后，旧 apply 任务仍在跑

**现状**

- `updates.js` 已有 `applyGeneration`，旧 apply 的 `finally` 不会清掉新 apply 的锁（ABA 已修）；
- 但「卡死 10 分钟 → 允许新 apply」只是**放锁**，没有真正终止旧任务；
- 旧任务如果晚到，仍可能继续写 `staging/`、更新 `downloadProgress`，甚至进入安装阶段。

**影响**

- 正常网络下几乎不触发；
- 极端情况下可能同时存在两个下载/安装任务，staging 文件互相覆盖。

**建议修法**

- 给 `apply()` 增加 `AbortController`，把 signal 贯穿 `updateFromZip` / `downloadTo`；
- 看门狗复位时 `abort()` 旧 controller；
- 安装前检查 generation，不是当前代就拒绝写入。

**验证**

- fixture 模拟旧 apply 卡住 → 触发新 apply → 旧任务返回时不能清锁、不能写 staging；
- 现有 `test-update-*` 增加一条代际断言。

### P1-2 agent 白名单按 `/api/socialV2/*` 前缀放行

**现状**

`src/bridge.js` 的 agent 白名单：

```js
url.pathname.startsWith('/api/socialV2/')
```

**影响**

- 新增任何 `socialV2` 端点，默认就对模型可见；
- 必须靠每个端点自己写 `x-agent-token` 检查，漏一处就是越权面；
- 这是设计风险，不是当前已发生的漏洞。

**建议修法**

- 改成显式端点表（allowlist per route），或给每个路由声明 `agent: true/false`；
- 管理类端点默认 `console only`；
- 加一条测试：遍历所有 `/api/socialV2/*` 路由，未声明 agent 的必须拒绝 agent token。

**为什么没直接改**

- 需要完整审计 40+ 路由；改漏会导致 AI 发不出消息，风险高于收益。

### P1-3 `saveSocialV2State()` 同步全量写盘

**现状**

- 每次调用把整个 `social-v2.json`（本机约 **436 KB**）同步序列化 + 原子写；
- 高频消息/唤醒时会在桥接事件循环里做磁盘 I/O；
- 本轮又新增了 `sessionTurns/sessionTokens/sessionBaseTokens/handoffPending/rolloverPending`，状态只会更大。

**影响**

- 状态越大，单次写越慢；
- 极端时可能拖慢唤醒/等待的响应。

**建议修法**

- 把「会话状态」拆成 append-only journal + 定时 compact；
- 或节流 `saveSocialV2State`（例如 200ms 合并写），但必须保证进程退出前 flush；
- 不能简单改异步写：会改变持久化时序，可能丢最后一次状态。

**为什么没直接改**

- 持久化时序是核心不变量；没有真机压力测试前不动。

### P1-4 换会话 P0 修复尚无真机长会话复验

**现状**

- 本地已改为「到阈值先 `rolloverPending`，下一轮投递前才退休」；
- purpose prompt 在拼 token 前 `forceRoll`；
- `purpose preview` 不触发滚动；
- 状态字段已持久化。

**缺口**

- 只在单元/静态断言层验证；
- 还没有测试机在超长会话上连续触发两次投递，确认「触发轮回复不再 403」。

**验证方式**

1. 找一个累计 token 远超 `rolloverTokens` 的会话；
2. 连续两次投递触发滚动；
3. 看 bridge.log：
   - 第一次只出现「下一轮投递开始前换会话」；
   - 第二次出现 `[rollover]`；
   - 同一轮不再出现「会话令牌校验失败」。

## P2（体验/工程性优化，可后置）

### P2-1 VBS 启动只验证 explorer spawn 成功

**现状**

- `spawnSnowLumaDetached()` 写 VBS，用 explorer 打开；
- 返回 `ok:true` 只代表 explorer 进程启动成功；
- 如果 `.vbs` 关联被策略禁用，wscript/node 可能根本没起来。

**影响**

- UI 可能显示「已启动 / 等待控制台」，实际没进程；
- 10 秒后返回 pending，用户需要自己看日志。

**建议**

- 启动后 2~3 秒检查 wscript/node 进程或端口；
- 失败返回结构化 `snowluma.launch-failed`，并提示 `launchMode=legacy`。

### P2-2 `release-manifest --verify` 不检查清单外的额外文件

**现状**

- 已改读被校验目录自己的 `release/install-manifest.json`；
- 缺失/改坏都会报错；
- 但目录里「清单之外多出来的文件」不会报。

**影响**

- 发布包被塞入额外文件仍可通过校验；
- 对「包完整性」门禁来说不够严格。

**建议**

- 只对**发布包目录**（非运行目录）做 extra-file 检查；
- 跳过 `config.json`、`state/`、`roles/`、用户数据目录；
- 增加「多一个未登记文件必须失败」测试。

---

### P2-3 `stopSnowLuma` 的 PID 启发式

**现状**

- 先找 5099/3000/3001 的监听 PID；
- 再要求命令行含 `index.mjs` 或 `SnowLuma`；
- 找不到端口时按 `SnowLuma.*index.mjs` 兜底。

**影响**

- 极端情况下可能误杀同端口、命令行含 `index.mjs` 的其它 node；
- 正常 SnowLuma 安装路径下不会触发。

**建议**

- 把 `snowluma.launcherPath` 传进 PowerShell，校验命令行包含安装根；
- 只杀匹配根目录的 PID，精确到进程路径。

### P2-4 非回环 WebUI host 的安全边界

**现状**

- `portOpen` 已支持 host；
- `webuiHost` 可配置；
- 但产品定位是「单机回环控制台」。

**影响**

- 配成局域网地址时，密码/Token 会走非回环网络；
- 目前没有 TLS 强制。

**建议**

- 非 `127.0.0.1`/`localhost` 时给出明确警告；
- 或只允许回环，其它值拒绝并提示。

---

### P2-5 旧 `batchWindowMs=8000` 不做自动迁移

**现状**

- 新默认是 6000；
- 测试机 `config.json` 里显式写了 8000，所以实际仍是群聊 8000ms；
- 这是「用户显式值优先」的正确行为，不是 bug。

**建议**

- 由产品决定是否做一次性迁移；
- 迁移必须可回滚、可解释，不能静默改用户配置。

### P2-6 配置模板缺段

**现状**

`config.example.json` 仍缺：

- `chat` 的顶层开关（`ownerQQ`、`groups`、`private`）；
- `platforms.start` 显式段；
- `pet` 段；
- `tokenBudget` 段。

**影响**

- 新用户/排障时看不到这些能力的默认值；
- 代码有硬编码默认，不会崩，但文档与模板不一致。

**建议**

- 补模板段，保持与 `store.js` 默认层一致；
- 加一条「模板键覆盖默认层」测试。

### P2-7 state ACL 收紧失败仍会告警

**现状**

- 启动时尝试 `icacls` 收紧 `<repo>/state`；
- 普通权限下可能 `ETIMEDOUT`/失败，日志会提示本机其它用户可能读到 token；
- 已把调用挪到监听之后，避免启动误报失败。

**影响**

- 安全加固不完整；
- 不影响功能，但属于真实安全债。

**建议**

- 安装/首次启动引导管理员执行一次；
- 或在控制台「访问与安全」页提供一键重试；
- 不自动提权。

### P2-8 安装目录跑 audit 的环境性失败

**现状**

- 源码树：`153/153`；
- 安装目录：约 `150/152`；
  - `test-audit-setup-guards`：安装包 `.bat` 是 LF，用例要求 CRLF；
  - `test-release-manifest`：安装目录没有 git ref，无法 `--verify-ref`。

**影响**

- 不是产品回归；
- 但会误导现场排障。

**建议**

- 测试用例区分「源码树」与「安装包」；
- 或发布时保留一个 `release/verify` 模式，不依赖 git。

### P2-9 版本更新进度：dev/version 没有真实总大小

**现状**

- stable/release 有 `asset.size` 时能显示真实百分比/包大小；
- dev/version 走 GitHub zipball，响应 `Transfer-Encoding: chunked`，没有 `Content-Length`；
- UI 已明确显示「已下载 X MB / 总大小未知」。

**影响**

- 用户看不到真实百分比；
- 不是计算错误，是上游归档不提供总大小。

**建议**

- 发布侧额外上传 zip asset，让 `assets[].size` 有值；
- 或改为自己托管带 Content-Length 的下载包。

### P2-10 单文件架构债

**现状**

- [src/bridge.js](src/bridge.js)：约 17.2k 行、约 180 个 `/api` 分支；
- [plugins/surfcore/lib/client.js](plugins/surfcore/lib/client.js)：约 8k 行；
- [plugins/surfcore/lib/index.js](plugins/surfcore/lib/index.js)：约 4.2k 行。

**影响**

- 改动影响面大，回归测试成本高；
- 新功能容易继续塞进主 `if` 链。

**建议**

- 先拆 HTTP 路由表（纯映射，不改行为）；
- 再拆会话生命周期（rollover/token/session）；
- 最后拆 B站/记忆卡服务；
- 每一步都保持接口与测试不变。
